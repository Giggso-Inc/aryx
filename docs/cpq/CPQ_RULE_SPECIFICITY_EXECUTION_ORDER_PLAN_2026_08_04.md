# CPQ Rule Specificity Execution Order — Plan (2026-08-04)

## Context

The user wants CPQ rule execution to consider broader-scoped ("product family") rules before narrower-scoped ("product line") rules before the most specific ("product"/model) rules — so that when rules disagree, the more specific one wins, the way business rules normally cascade.

Investigation ruled out a literal schema field: BigMachines' own `bm_config_rule` has no family/line/product tag (`rule_area` is `1` for 711 of 712 real rules in the APX Next export, `rule_sub_type` is `0` for all 712 — no signal). The user confirmed the right definition instead: a rule's "level" should come from what its own **condition** references — an existing, already-shipped dependency graph in this codebase (`CpqEngine._dependency_ordered_keys`, built for a different purpose — payload JSON key ordering) already proves attributes gate each other (e.g. Hardware Version gates Product Selection via a real constraint rule). Depth in that same gating graph is a generic, catalog-agnostic stand-in for family/line/product — no attribute names or catalog specifics are ever hardcoded.

This also fixes two real, verified gaps: `apply_hiding_rules` and `apply_recommendation_rules` resolve same-target rule conflicts via `list.add()/.discard()`/dict-overwrite in **whatever order `fetch_rules()` happens to return** — confirmed via direct code read that neither the Postgres nor Oracle `fetch_rules`/`fetch_value_rules` SQL has an `ORDER BY` clause. Today that's arbitrary; ranking rules by specificity makes "the more specific rule wins" the actual, deterministic behavior instead.

**Real-data risk check (done during planning, not hypothetical):** audited the live APX Next catalog (workspace 39004, 396 hiding rules, 588 recommendation rules, 215 constraint rules).

- **Hiding rules: provably a no-op today.** 115 attrs are targeted by 2+ hiding rules, but **0** of them have a genuine `hide=True` vs `hide=False` disagreement — every shared target's rules agree (they're just different OR-condition paths to the same outcome). Reordering is safe but doesn't change any real behavior right now — still worth doing for future-proofing and determinism.
- **Recommendation rules: a real, non-trivial risk surface.** 93 attrs are targeted by 2+ recommendation rules, and **33** of those have genuinely different recommended values across their rules (e.g. attr `17691442144` has candidate values `{BLACK, GREEN, SCRIPT}`). This is where order can and likely does affect live behavior today, and where this change needs the most careful testing before being trusted.
- Constraint rules don't need reordering at all — `apply_constraint_rules`' intersection (`_intersect`) is commutative; order can never change its result.

## Approach

Add three new methods to `CpqEngine` in `src/aryx/cpq/engine.py`, reusing (via extraction, not by calling directly) the id-resolution/edge logic `_dependency_ordered_keys` (lines ~7307-7391) already has:

1. **`_rule_condition_edges(attrs, rules) -> (predecessors, successors, id_to_vn)`** — factor the shared, *unfiltered* part out of `_dependency_ordered_keys`: `id_to_vn` (from `ConfigAttr.entity_id`, then `source_id`-preferred override) and one edge per rule from each `conditions` tuple's `attr_id` (or the scalar `condition_attr_id` fallback) into its `target_attr_id`. Critically, do **not** restrict to a `key_set` like the payload version does (that filtering is specific to "only order what's about to be emitted" and would wrongly zero out predecessors for hidden/unfilled attrs). `_dependency_ordered_keys` is refactored to call this same helper and apply its own `key_set` restriction on top, so both features share one source of truth for the fiddly id-resolution logic.
2. **`_attribute_depth_ranks(attrs, rules) -> dict[str, int]`** — longest-path-from-root depth over the graph from (1), via the same Kahn's-algorithm peel `_dependency_ordered_keys` uses (zero-in-degree nodes = depth 0, each successor's depth = `max(current, predecessor_depth + 1)` as nodes are emitted). Cycle-safe: nodes that never reach zero in-degree (a genuine cycle, or downstream of one) get `max(all resolved depths) + 1` — never depth 0, which would wrongly promote an unverifiable/ambiguous rule to "most trusted." Tie-break by `ConfigAttr.order`.
3. **`rank_rules_by_specificity(attrs, hiding_rules, rec_rules, con_rules) -> (hiding_rules, rec_rules, con_rules)`** — builds one combined depth map from `[*hiding_rules, *rec_rules]` (constraint rules excluded from the graph and from reordering, per the no-op finding above — passed straight through, unmodified), then **stable**-sorts `hiding_rules` and `rec_rules` independently by each rule's own specificity rank = max depth among the attribute(s) its `conditions`/`condition_attr_id` reference. Rules with no resolvable condition attribute at all (script-backed with no declarative conditions) rank **first** (lowest/coarsest), not last — an unverifiable rule should never get default authority to override a rule whose specificity is provably known; this matches this codebase's existing "when unknown, don't let it win" pattern (`apply_hiding_rules`' unknown-script case leaves things visible rather than hiding; `apply_recommendation_rules`/`apply_constraint_rules` skip firing on an unresolved script rather than guessing).

Wire this **once**, at the very top of `CpqEngine.evaluate_rules_loop` (`engine.py:3860`), before its `for _ in range(_MAX_LOOPS)` loop — using the untouched `attrs` parameter as passed into the function (not a loop-local reassignment; `apply_hiding_rules` shrinks `attrs` on every pass, so ranking must happen once against the full, pre-loop set). This is a single change point: every caller of `evaluate_rules_loop` gets deterministic, specificity-ordered rule application automatically, with zero call-site changes anywhere in `ask_api.py`.

## Critical files

- `src/aryx/cpq/engine.py` — the three new methods; refactor of `_dependency_ordered_keys` (~7307-7391) to share the edge-extraction helper; one new call at the top of `evaluate_rules_loop` (~3860-3901).
- `src/aryx/cpq/state.py` — no changes; existing `HidingRule`/`RecommendationRule`/`ConstraintRule` fields (`condition_attr_id`, `target_attr_id`, `conditions`, `script`) are read-only inputs to the new logic.
- `tests/test_cpq_rule_specificity_rank.py` (new) — unit tests for the depth ranker in isolation.
- `tests/test_cpq_e2e.py` or a new `tests/test_cpq_rule_execution_order.py` — the conflict-resolution proof tests, modeled on the existing `tests/test_cpq_hardware_before_product.py` / `tests/test_cpq_payload_dependency_order.py` synthetic-fixture style.

## Testing plan

1. **Depth-ranker unit tests** (synthetic attrs/rules, not real catalog data — proves catalog-agnosticism): simple chain (depths 0,1,2), a diamond (two independent parents converging on one child → child depth = max(parents)+1), a genuine 2-rule cross-reference cycle (assert no infinite loop, deterministic non-zero fallback depth), a script-backed rule with no conditions (assert it lands in the lowest/first-ranked tier), and a no-rules-at-all case (assert pure `ConfigAttr.order` fallback — zero behavior change for catalogs with no declarative rule conditions).
2. **The test that actually proves the fix**: two `HidingRule`s targeting the same attribute — one on a shallow/broad condition, one on a deep/narrow condition (mirror the real Hardware-Version-gates-Product-Selection shape) — constructed so they disagree. Feed `rank_rules_by_specificity`'s output into `apply_hiding_rules` under **both** raw input orders (`[narrow, broad]` and `[broad, narrow]`) and assert both converge to the identical, narrow-wins result. Same test shape for two `RecommendationRule`s with different values on the same unfilled target.
3. **A test replaying a real conflict**: recreate the shape of real attr `17691442144` (BLACK/GREEN/SCRIPT candidates from the live audit) with synthetic conditions mirroring realistic specificity levels, and confirm deterministic resolution both ways.
4. **Regression**: re-run `test_cpq_hardware_before_product.py` and `test_cpq_payload_dependency_order.py` unmodified, plus add one assertion in each that `rank(Hardware Version) < rank(Product Selection)` from the new function — closing the loop with the already-shipped layout feature without merging the two code paths. Run the full existing CPQ suite to confirm no unrelated regressions (expected: none, since the sort only changes behavior for provably-conflicting same-target rules, which is a small, now-enumerated subset).
