Part 1 · The main thread

Eight steps, one conversation

_run_cpq_turn() (src/aryx/api/ask_api.py) drives every turn through the same eight stages. Most turns skip straight to Step 3 once the product and country are known — the full sequence only plays out once, at the very start of a quote.

Deterministic (engine/rules) Waiting on the customer Narrated by the LLM (with a fallback)

STEP 1

Anchor validation

waits for product + country

Nothing else can run until the product family and destination country are known. detect_product_mention() tries to resolve the family from free text first; if it can't, the engine lists the families actually ingested in this workspace rather than a hardcoded guess.

2
STEP 2

Value mapping

catalog lookup

The resolved product name is matched against the catalog's real productSelectionProduct_all option list via apply_answer() — fuzzy option matching, never a raw string passthrough. load_product_config() then loads every ConfigAttr for this catalog, scoped by catalog_prefix so a workspace holding two ingested products never cross-contaminates rules.

3
STEP 3

Rule evaluation loop

runs on every turn

Hide → recommend → constrain → auto-fill, repeated until nothing changes (evaluate_rules_loop(), capped at 8 passes). This is the engine's core — see Part 2 for what happens inside it.

4
STEP 4

Hybrid prompting

asks the customer

Whatever the loop couldn't resolve becomes pending. The first pending attribute is asked with a plain-English context sentence (build_context_sentence() — "Since we locked in X, please choose Y") plus its numbered real option list, never a raw internal field name.

5
STEP 5

Lock & loop

re-enters Step 3

The customer's reply is matched against that attribute's real options and locked in with filled_source = "user" — a provenance tag the rest of the engine treats specially (see the "never silently re-guess" principle below). Control returns to Step 3.

6
STEP 6

Review & cascade

LLM-narrated summary

Once nothing is left pending, a categorized summary is narrated in plain prose (_cpq_summary_text()) — Product, Service Plan, Quantity & Duration, and a curated "Associated Options" catch-all. If the narration call fails, a deterministic bullet renderer (render_filled_summary()) takes over instead — the flow never blocks on the model being reachable. Changing anything from here re-invalidates dependents and re-runs Step 3.

Real turn
Changing Hardware Version mid-review: "Because Hardware Version changed, Product depends on it and needs a fresh value — recalculating now." The new JSON reflects every recalculated dependent, not just the one field named.
7
STEP 7

Contextual Q&A

graph + LLM synthesis

A genuine question ("what's included with the Video RSM?") pauses the configuration, answers from the graph, then re-shows exactly where the conversation left off. A question about one attribute's own available options is answered straight from attr.options already in memory — no graph query, no LLM call needed for that fast path.

8
STEP 8

JSON payload synthesis

only on "confirm"

build_payload() assembles the real BOM API shape — per-type serialization (bare booleans, {"value","displayValue"} menus, {"items":[...]} multi-selects) — and excludes anything that was never a real customer decision (transient UI fields, flow-excluded mirrors, an active hiding rule's own match). The JSON is only ever generated here, never shown unasked before this.

Part 2 · Step 3, expanded

Inside the rule evaluation loop

This is the only place a value gets assigned without the customer typing it — so it's the one part of the engine held to the strictest "never guess" discipline.

1 · Hide

Hiding rules

apply_hiding_rules() — reveals or hides attributes based on what's already filled. Runs first so auto-fill only ever considers visible fields.

→
2 · Fill

Auto-fill

auto_fill() — hint match, then a valid catalog default, then a rule-governed pick. Blind guessing only ever happens for genuinely optional fields, and never overrides a value the customer already answered this turn.

→
3 · Recommend

Recommendation rules

apply_recommendation_rules() — a condition-matched rule fills a target field with its recommended value, e.g. Region derived from Country.

→
4 · Constrain

Constraint rules

apply_constraint_rules() — narrows which options remain valid for a field given the rest of the state. Multiple active constraints intersect.

repeats until nothing changes — capped at 8 passes per turn
rule_type = 11

Hiding rules

Show or hide a field when a condition is met. ~62% of real hiding rules in a production catalog are BML-script-backed, not a single condition/value pair.

rule_type = 10

Recommendation rules

Auto-select a value for a target field when its condition holds — the mechanism behind the Billing Option / CapEx Purchase example below.

rule_type = 5

Constraint rules

Narrow the allowed option set for a field — e.g. Region = NA restricts Frequency Band to only the codes valid in North America.

Tier 1 · default

A real deterministic parser for the BigMachines script language — regex-based condition and assignment matching. Handles the large majority of real scripts with zero model calls.

Tier 2 · off by default

LLM fallback for scripts Tier 1 can't parse. Gated behind ARYX_BML_USE_LLM=false — a slow/rate-limited call inside a live request is a real risk this flag exists to avoid.

Saying "confirm" shows the JSON — it doesn't lock the conversation. The same session keeps accepting Q&A and edits, re-showing updated JSON after every change, exactly like it did before confirmation.

Part 4 · What holds the whole thing together

Never a guessed value in the final quote

Three rules, enforced (or actively being hardened) across every step above.

01

Deterministic first, LLM for narration only

Intent detection, rule evaluation, and cascading are all regex/rule-graph mechanics — no model call decides what value goes in the payload. The LLM writes the prose summary and handles genuinely loose phrasing, always with a non-LLM fallback if it fails.

verified live · Gemini reason-tier misconfig fell back cleanly
02

A real decision is re-asked, never re-guessed

When a cascade invalidates a value the customer explicitly chose (filled_source == "user"), the engine asks again instead of silently substituting something else — user_answered_dropped_ids is the mechanism, extended twice this session to close gaps it didn't originally cover.

hardening in progress · docs/CPQ_USER_VALUE_PRECEDENCE_PLAN.md
03

A collision is disambiguated, never silently resolved

Two catalog fields sharing one display label ("Mounting Type" appearing twice) must never resolve to "whichever is first in the list" — the customer is asked which one, and the reply is remembered across the next turn.

fixed · deterministic match, gated LLM fallback for loose phrasing
