CPQ engine · technical flow

What actually decides which questions get asked, in what order, and when the engine refuses to guess — traced through cpq/engine.py, cpq/intent_gateway.py, and api/ask_api.py as they run today.

1 Entry & intent routing ask_api.py · cpq/intent_gateway.py

Every message arrives as free text with no guaranteed structure. Before anything else, the gateway decides whether this turn is safe to act on, needs a clarifying question, or should fall through to the older deterministic detector.

LLM classify
complete_json against the candidate bundle for this turn
›
dispatch
Safe to act — value resolved against OUR candidate list, never taken as free text from the model
›
clarify
Ambiguous — ask the user, don't guess between candidates
›
fallback
Timeout, schema failure, or empty question — defer to the deterministic path
🔒
The model never picks the value directly

GatewayDecision.value_display is resolved from a value_ref the model returns, matched against candidate bundles built in our own code (build_candidate_bundles) — a hallucinated value that isn't in the candidate list simply can't reach the session state.

2 Three file types feed the catalog — one skips the database entirely pipeline/doc_discovery.py · cpq/data_table_resolver.py

DATA_EXTS = {".json", ".csv", ".xml", ".xlsx"} — CPQ ingestion only actually exercises two of those plus one file type that never touches the database at all.

📦
.xml — the raw catalog export
Oracle CPQ's native export format. Never queried directly — the pipeline explodes it into one CSV per element type first, so the same FK-detection code handles every source uniformly.
_xml_to_csvs()
📊
.csv — Data Tables
Either exploded from the XML above, or ingested directly. Identified by column shape, never by filename — the same detector works across every customer's catalog.
data_table_resolver.py
📄
.txt — layout export
Read straight off disk at runtime, never ingested into Oracle at all. Display order only — see Layer 4.
config_layouts/*.txt

Four column-shapes the .csv Data Tables resolve to

Sequence-shaped
e.g. AttrSequence — every AttrName's optionOrReqFlag for a (cpq_model, base_model) pair. This is Tier C's mandatory-field source.
Hierarchy-shaped
e.g. CPQModelHierarchy.csv — maps a Product name to its coarser CPQModel product-family code.
Region-rule-shaped
e.g. NewCountryRegMapping.csv — model/value/region/ruleType/attribute rows; resolves the one ALLOW value for a region (+country).
Series-mapping-shaped
e.g. Seriesmodelsmapping.csv — resolves which real CPQModel variant applies for a region/country condition, keyed by attrN/opN/valN triples.
3 Session state & the three attribute tiers session_data · mandatory_tier_c_vns()

One session_data dict carries the whole conversation forward: filled, pending_variables, turn, status — round-tripped to the client and back on every message. Which fields still need an answer is decided by three tiers, not one flat list:

TIER A
User-answered
filled_source == "user" — the customer typed or picked this value directly.
TIER B
Rule / default-filled
Resolved by a business rule or a data-table default before the customer ever saw it.
TIER C
Catalog-mandatory, still unresolved
mandatory_tier_c_vns() — attribute names the real ingested AttrSequence Data Table flags optionOrReqFlag == "R" for the active (cpq_model, base_model). Catches fields Tier A/B miss entirely because they were defaulted, not user-answered — this is what's driving "Mounting Type", "Solution Set", "Solution Feature", and "Product" showing up as required, and it's read live from the catalog, not hardcoded.

This is what the Oracle env-var bug broke

ARYX_CPQ_LAYOUT_DIR was missing from docker-compose-oci.yml, so LocalDirLayoutFileSource fell back to cwd (/app) instead of /app/config_layouts — every lookup silently returned no match. It never changed which fields were mandatory (that's Tier C, above, reading straight from Oracle) — only the display order in the beautify/summary block went unranked.
