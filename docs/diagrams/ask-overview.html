What happens when someone asks a question

Ask turns a plain-English question into a grounded, cited answer, checking its own work before it ever shows you a result.

STEP 01

Ask

Plain English
InA question, in your own words→OutA question ready to search on

Someone types a question the way they'd ask a colleague, no query language, no dashboard to build first.

Why it matters — anyone can get an answer, not just the person who knows how the data is structured.

STEP 02

Retrieve

Search the graph
InA question ready to search on→OutThe relevant records and connections

Aryx looks through the knowledge graph and pulls out the specific records and connections relevant to the question.

Why it matters — this step follows fixed, predictable rules rather than letting the AI decide what to look at, so results are consistent.

STEP 03

Answer

Drafted response
InThe retrieved evidence→OutA draft plain-English answer, with citations

The AI turns the retrieved evidence into a clear, plain-English answer, with the original source records cited alongside it.

Why it matters — you can always click through and see exactly where an answer came from.

STEP 04

Ground

Check the answer
InThe draft answer→OutA verified answer, unconfirmed claims flagged

The draft answer is checked against the evidence that was actually retrieved for it. Anything the answer claims that isn't backed up by a real record is flagged rather than shown as fact.

Why it matters — this is what keeps Ask from ever confidently making something up, checked after every answer, not just trusted upfront.

Automatic check, no AI involved

This is a plain match against the evidence, not another AI judgment call, so it can't itself get this part wrong. It runs every time, on every answer, with zero exceptions.

STEP 05

Continue

Stay in context
InThe answer just given→OutContext for the next question

The conversation remembers what was already asked, so a follow-up question builds naturally on the last answer instead of starting from scratch.

Why it matters — it works like a real conversation, not a series of disconnected searches.

For the technical folks in the room

Under the hood: how Ask actually flows, step by step

The same five steps from above, broken into 13, each one showing exactly what feeds into it and what it hands to the step after, including precisely where the database and the AI models get called, and where the flow branches into a dedicated path for product-configuration questions.

STEP 01

Browser opens the request

Client
InSomeone types a question→OutAn HTTP request carrying the question text

Someone using Aryx types a question in their regular web browser.

Why it matters — nothing special has to be installed; it starts the same way any web page does.

Example — the actual request shape (AskRequest)
{
  "question": "What does the Hide UDCC rule affect?",
  "workspace_id": 13,
  "session_data": {},
  "history": []
}
On a brand-new conversation, session_data starts empty. history holds prior turns' role/text pairs, for a follow-up question it would already have entries.
STEP 02

Web App forwards it to the API

Next.js UI
InQuestion text from the browser→OutThe same request, forwarded to the core service

The Ask screen passes the question to the API over one internal connection.

Why it matters — the browser only ever talks to one place, so there's nothing extra to configure or secure separately.

Example — what actually goes over the wire internally
POST /api/ask
x-aryx-api-key: •••• (added here, never sent to the browser)

{ "question": "What does the Hide UDCC rule affect?",
  "workspace_id": 13, "session_data": {} }
The request body the browser sent is passed through unchanged; only the internal API key is added at this hop.
Alternate entry: Agent tools

Outside AI assistants (Claude, Cursor, and similar) can ask Aryx directly here too, through the same door, under the same rules.

STEP 03

API checks who's asking

Core service
InForwarded request→OutAn authorized request, scoped to one workspace

Before anything else happens, the API confirms the request is authorized and scoped to the right workspace.

Why it matters — one team's data is never reachable from another team's question, even by accident.

Example — the check
workspace_id=13 is confirmed to belong to the caller's API key before question is even looked at.
STEP 04

Aryx decides: general question, or product configuration?

Conditional route
InThe authorized request→OutRouted to the general path (STEP 05) or the CPQ path (STEP 09)

Before doing any retrieval, Aryx checks two things: does the incoming session_data already say this conversation is mid-configuration (mode: "cpq"), or, if it's a fresh conversation, does the question itself read as a request to configure or price a product? Either one routes to the CPQ path; a session already in CPQ mode stays there even if the wording of this particular message looks generic.

Why it matters — quotes have to obey the real catalog's rules, what's hidden, what's required, what's restricted; a general-purpose retrieve-and-answer flow can't be trusted to get that right, so it's routed differently from the start.

Example — two real questions, two real routes
"What does the Hide UDCC rule affect?"session_data={} and not a configure request → general path (STEP 05)
"Help me configure a Product"detected as a configure request → CPQ path (STEP 09), session_data will come back with mode="cpq"
Once a session's session_data.mode is "cpq", every following turn in that conversation routes here automatically, the catalog rule that governs Hide UDCC for Non-Privileged Users stays enforced for the whole conversation, not just the turn that started it.
STEP 05

PostgreSQL is queried

Database read · general path
InA general (non-CPQ) question→OutCandidate records matching the question's terms

For everything that isn't a product-configuration conversation, the API's first move is to look up whatever records already exist relevant to the question, in PostgreSQL, the single source of truth.

Why it matters — nothing is trusted until it's confirmed against the real, durable data.

Example — one retrieved entity (RetrievedEntity)
{
  "id": 47633456,
  "type": "Rule",
  "name": "Hide UDCC for Non-Privileged Users",
  "attributes": { "rule_type": 11 }
}
"Hide UDCC" in the question is enough to match this rule's name in PostgreSQL. Its neighbors and sources lists start empty here, FalkorDB fills those in next.
STEP 06

FalkorDB is queried

Graph read · general path
InCandidate records→OutTheir connections and neighbors in the graph

The API follows the connections between those records in the knowledge graph, who's linked to what. This is the technical version of Retrieve, above.

Why it matters — this is what turns a handful of records into a genuinely connected answer.

Example — the same entity, now with neighbors filled in
"neighbors": [
  { "id": 39426962, "type": "ConfigAttribute", "relation": "HIDES" },
  { "id": 43022701, "type": "ConfigAttribute", "relation": "HIDES" }
]
This is what actually answers "what does the rule affect": the two attribute IDs it hides, discovered by walking the graph edge built back at ingestion's Relate step.
STEP 07

An AI Model is called

AI call · general path
InRetrieved records + connections→OutA draft plain-English answer, with citations

The retrieved evidence, not a blank slate, is handed to an AI model to reason over and draft a plain-English answer from.

Why it matters — the AI only ever reasons over facts already confirmed in steps 5-6; it doesn't get to invent them.

Example — the draft answer
"The Hide UDCC for Non-Privileged Users rule hides two catalog settings unless a privileged-user flag is set to YES." The AI only names entities it was actually handed, not ones it recalls from training.
STEP 08

The draft answer is grounded

No AI, plain matching · general path
InThe draft answer→OutA verified answer, unconfirmed claims flagged

The draft answer is checked, by plain text matching, against the records that were actually retrieved for it, not another AI judgment call. Anything the answer claims that isn't backed up is flagged, not shown as fact.

Why it matters — this happens automatically, on every single answer, after the AI has spoken, not before, and it can't itself hallucinate, since it isn't making a judgment call, just checking for a match.

Example — the actual Grounding record, and what the browser receives
"grounding": {
  "grounded": true, "entity_count": 3, "cited_count": 3,
  "source_count": 1, "score": 1.0,
  "citations": [{ "marker": 1, "entity_id": 47633456,
                  "entity_name": "Hide UDCC for Non-Privileged Users",
                  "entity_type": "Rule" }],
  "uncited_entities": []
}
The final response to the browser also carries answer, terms, tools_called, and usage (token counts, latency, which models were used) alongside this. An empty uncited_entities list means nothing retrieved got left out of the answer unexplained; anything that did would be named here.
STEP 09

Catalog attributes and rules are loaded, fresh

Database read · CPQ path
InThe CPQ session (new or continuing) + which catalog→OutThis turn's attributes and rules

The configuration assistant reads the catalog's attributes and every rule that governs them straight from PostgreSQL again, every single turn, never carried over or cached from earlier in the conversation.

Why it matters — a correction to a rule is picked up on the very next turn, without needing to restart the conversation.

Example — the same real catalog data from ingestion
This turn loads the Product attribute and the Hide UDCC for Non-Privileged Users rule ingested earlier, along with everything else in this catalog.
How the session actually works

The API itself keeps no memory between turns. The entire session, every answer filled in so far, is a plain object the browser sends back on every request (session_data) and gets back updated on every response. Nothing about "where this conversation is" lives on the server between calls.

STEP 10

Rules are evaluated in a loop, until nothing changes

Mostly deterministic · CPQ path
InThis turn's rules + the answers filled in so far→OutA settled set of visible, hidden, and auto-filled attributes

For the answers given so far in this conversation, each rule's condition is checked, hide, then auto-fill, then recommend, then constrain, and the whole pass repeats from the top, since hiding one field can change what should be auto-filled next, which can trigger another rule. It stops once nothing changes, or after 8 passes. Most conditions are checked directly and deterministically; a minority of rules are written as legacy scripts too complex to parse directly, for those, an AI model is asked what the script would decide.

Why it matters — a single pass isn't enough to guarantee a consistent result; looping to a fixed point is what makes the outcome the same regardless of which order rules happened to fire in.

Example — the session's answers so far, and a real rule firing
"filled": {
  "isPrivilegedUser": "NO",
  "productSelectionProduct_all": "APX6500"
},
"filled_source": {
  "isPrivilegedUser": "user",
  "productSelectionProduct_all": "user"
}
Reading straight from filled: the privileged-user flag is NO, not YES, so Hide UDCC for Non-Privileged Users fires. Attribute 39426962 and attribute 43022701 are removed from what will be asked or shown next. filled_source records that both values came from the user directly, not a default or an earlier rule, useful later for explaining why a field has the value it does.
STEP 11

The next question, or the final quote, is decided

CPQ path
InWhatever's still visible and unanswered after the loop settles→OutThe next question to ask, or a finished quote

Once the rule loop stops changing anything, the assistant looks at what's left. If there's still a visible, unanswered attribute, that becomes the next question. If nothing's left to ask, the filled answers become the finished quote.

Why it matters — this is what makes the conversation feel guided rather than like filling out a long form, only ever asking about what's still actually relevant, given everything hidden or auto-filled above.

Example — the next question, and the session going back out
The next unanswered, un-hidden attribute becomes the question text itself, phrased in plain English with its options listed inline, there's no separate structured "options" field, the question and its choices are one piece of text. Alongside it, session_data goes back to the browser with filled, turn incremented, and status: "configuring", ready to be sent right back on the next request at STEP 01.
STEP 12

Conversation is stored in PostgreSQL

Database write · both paths
InThe verified answer, or the CPQ session's next question/quote→OutA stored conversation row

Whichever path this turn took, the question, the result, and its citations or session state are saved back to PostgreSQL, so the next turn in this conversation has full context.

Why it matters — this is what makes Continue, above, possible: nothing about the conversation only lives in the browser tab.

Example — what's stored for each path
General paththe question, the answer text, and the grounding/citations shown above
CPQ paththe question, the next question asked back, and the full session_data (filled, filled_source, turn, status)
STEP 13

The result returns to the screen

Response · both paths
InStored result→OutRendered response in the browser

The finished result, a cited answer, or the next quoting question, travels back through the API, to the Web App, and onto the browser, the same round trip every time.

Why it matters — a quick question and a long product-configuration conversation both follow this identical, predictable path back to the screen.

Example — the two real response shapes
// general path
{ "answer": "...", "terms": [...], "tools_called": [...],
  "usage": {...}, "grounding": {...} }

// CPQ path
{ "answer": "...", "terms": [...], "tools_called": [...],
  "usage": {...}, "grounding": null,
  "session_data": { "filled": {...}, "turn": 2, ... },
  "cpq_payload": null }
The CPQ response carries session_data forward so the browser can send it right back on the next question, that round trip is the entire mechanism behind "how the session works." cpq_payload stays null until the quote is actually finished and approved.
