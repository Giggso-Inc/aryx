Aryx on Oracle ADB

One shared Oracle Autonomous Database sits behind every service in the stack. This is how the pieces connect to it, and to each other, in the OCI deployment.

Overview

Where Oracle sits in the stack

Four services run in Docker; all four reach the same database. Nothing talks to Oracle except through api, shay-api, or mcp — the browser and web never do.

Component reference

How each service reaches Oracle

Same physical database, three different connection methods — the sync thin client, the async thin client, and PGX's own graph load.

Component Reaches Method What it's for
api Aryx data oracledb thin, sync Entities, ontology, ask threads, CPQ, jobs — all core reads/writes.
api Property graph oracledb thin, sync Direct SQL/PGQ reads — same pool as the data above, no intermediary.
shay-api Shay data oracledb thin, async Its own tables, created via SQLAlchemy on first boot.
shay-api api HTTPS + shared key 9 endpoints: workspace bridge (ensure/update/delete/mapping), chat ask, doc read/summary/confirm, job status.
mcp Aryx data oracledb thin, sync Only for bearer-token auth and direct action execution — most tool calls go through api instead.
web api · shay-api HTTPS + shared key Never touches Oracle directly.

Request path

A chat message, end to end

What happens between a browser message and Oracle answering it.

  1. Browser posts a message; web's server-side route checks the session, then forwards to api with a shared API key attached.

  2. api verifies that key against Oracle-backed settings before the route runs.

  3. The Shay bridge store upserts the thread's mapping row in Oracle — an explicit MERGE, in place of the Postgres syntax the code was first written against.

  4. The CPQ engine reads which fields are mandatory live from Oracle's ingested catalog table, plus a layout file for display order.

  5. Each model call routes through OCI GenAI, then usage gets logged back to Oracle.

  6. The reply streams back through api → web → browser, the same key-checked path in reverse.

Not shown

Configured, but not wired up

Two pieces exist in the compose file and settings but have no actual call site in the codebase, so they're left off the diagram above rather than drawn as working connections.

  • pgx-server — PGX_SERVER_URL is declared but never read anywhere in the code, and the container itself only starts with an explicit --profile pgx flag.
  • Object Storage buckets — namespace and bucket names are configured, but no ObjectStorageClient, upload, or download call exists in the pipeline.
