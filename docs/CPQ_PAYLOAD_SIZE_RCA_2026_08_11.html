Why the quote has 30+ fields instead of the 9 we expect

A plain-language look at why Aryx's quote comes back much bigger than the reference quote the client is used to seeing, with the layout order, the AJAX flag, and the "hide=false / empty default" theories all checked directly against the real catalog data.

The Problem

When a customer configures an APX Next radio, the client expects the final quote to list around 8–10 fields — the handful of things the customer actually chose or that identify the product. Instead, Aryx is returning roughly 30 fields — three times as many.

Nothing in the extra fields is wrong — every value is a real, valid catalog option. The problem is volume: Aryx is filling in and shipping a lot of detail nobody asked it to decide.

Question 1 — Is the 95% AJAX figure about all 30 fields, or the whole catalog?

It's about the fields in this quote specifically — not the whole catalog. We checked both numbers directly:

97%
of the 32 fields in THIS quote are AJAX-tagged (31 of 32)
59%
of ALL 429 fields in the whole catalog are AJAX-tagged (252 of 429)

That gap matters: fields in this quote are far more likely to be AJAX-tagged than an average catalog field. That's exactly what we'd expect if Aryx is disproportionately pulling in "loads later" sections — those sections are almost entirely AJAX-tagged, while the catalog as a whole is a roughly even mix.

Question 2 — Does the real layout confirm these extra fields belong to later steps?

Yes. We pulled each field's position in the real customer-facing layout file (the same file that drives the actual order fields appear in on the real ordering website) and sorted every field in this quote by that real position. The 9 fields the client expects cluster almost entirely in the first 1,700 lines of an 18,500+ line layout. Nearly every extra field sits far later — several past line 4,000, one as far down as line 18,508.

Two small exceptions worth flagging honestly: extendRangeTo762764MHz_astro (line 947) and languageLanguageType_astro (line 1169) sit early in the layout alongside the core 9, yet weren't on the client's expected list. These two may be genuinely early-form fields worth a second look, separate from the "later section" pattern.

Questions 3 & 4 — Checked Again, Against the Real Layout File

The client's exact rule was: "hide = false AND defaultValue is not empty → the field should show up in the final output." Our first pass checked the wrong data source — the raw catalog's business rules and the raw catalog attribute's own factory default. The client meant the layout file itself (Config Layout APXNext.txt), which has its own literal "hide" and "defaultValue" setting on every single field placement — a separate, more direct source than either of those. Re-checked against the real layout data for all 32 fields currently in Aryx's payload:

32 / 32
have hide: false in the layout — true for every single one, no exceptions
4 / 32
ALSO have a non-empty defaultValue in the layout
This is the real, direct answer. hide=false carries no diagnostic power on its own here — it's true for every field in this payload, with zero variation. But defaultValue does vary, and by the client's own rule, only fields with BOTH conditions true should be auto-populated. Only 4 of the 32 fields qualify: modelSelectionFrequencyBands_astro ("700/800 MHZ"), antennasType_astro ("WHIP APX NEXT"), beltClipType_astro ("2.0 INCH / 5.08 CM (STANDARD)"), and solutionTypeDevices_astro ("RADIOCENTRAL PLUS CPS PROGRAMMING"). The remaining 28 fields have no layout default at all — Aryx is auto-filling them with no basis in the layout's own configuration, purely from its own rule-resolution or "pick the first legal option" logic.

This lines up with — and sharpens — the catalog-level check we ran first: the raw catalog attribute record also shows an empty default for all 32 fields. The layout file is the more directly relevant source (it's what actually drives the real ordering UI), and it draws the exact same line the client's rule predicts: a small, specific set of fields (4, not 9) have a real default anywhere in the system; everything else is Aryx's own invention.

Root Cause

Here's the simple version: the real Motorola ordering website is built like a multi-step wizard. The customer answers a few core questions up front, and everything else — battery, antenna, training, service coverage — only appears later, in separate sections that load one at a time as the customer scrolls or clicks further into the form. Those later sections use a web technique called AJAX, which loads a section of the page on demand instead of all at once.

Aryx doesn't have that step-by-step concept. It treats the entire order form as one flat list of fields and tries to resolve everything on that list in a single pass — including all those later, AJAX-loaded sections the customer never actually got to in the real website. Wherever Aryx can pick a sensible-looking default (a rule, or "just take the first valid option"), it does — and then includes that guess in the final quote as if the customer had chosen it.

In one sentence: Aryx is finishing the whole order form on the customer's behalf, including sections the real website would only reveal much later — and shipping all of that guesswork in the quote, because none of these fields have a catalog default AND none of them are ever explicitly forced visible — they're just never told "not yet."

What This Means for the Fix

This isn't a data-quality bug — every value Aryx sends is real and catalog-valid. It's a scope problem: Aryx needs a way to know which fields belong to "the part of the form the customer has actually reached" versus "later sections that shouldn't be resolved or shipped yet." Given the empty-default finding above, one concrete signal is already sitting in the data: a field with no catalog default AND no rule/customer input yet is a strong candidate for "leave it out of the quote for now." Options worth discussing:

  • Only include fields the customer actually answered, plus fields a rule requires to make sense of those answers — drop everything else from the quote until asked.
  • Use the AJAX flag and/or layout position as a signal for "later section" fields, and hold those back from the quote by default.
  • Introduce a "quick quote" vs. "full build sheet" distinction, so the client can choose which one they want back.

Each of these is a real, scoped option — not yet decided. The next step is picking one and reproducing it end-to-end before touching any code.
