Aryx Agents — SOP deep dive

Exhaustive reference for what is (and is not) an agent in Aryx: augmented LLM patterns, hub-and-spoke orchestration, pipeline chains, peer/blackboard coordination, model tiers, MCP external agents, internal discovery agents, intent classification, Raven/Andie multi-agent development, tool matrices, state, and where to read the logs.

SOP grade Offline HTML MCP + internal No fake “Agent OS” product — real code paths only

1. Overview & honesty first

There is no single Python package named agents/ in the runtime product. “Agent” in Aryx is a role: any component that (a) uses an LLM (or external model host) to decide, (b) may call tools / side-effect systems, and (c) operates under a correlation id (workspace, job, run_id).

What ships in production runtime

Internal pipeline agents (schema, doc discover, tag, relate), Ask/CPQ augmented LLM, Intent gateway agent, MCP tool server for external hosts, kinetic act (always pending).

What is outer-loop (engineering)

Raven + Andie + specialist skills (hub-spoke multi-agent for coding). Lives under .claude/skills/ — not the customer-facing API process.

SOP rule: When someone asks “where is the multi-agent system?”, answer with which plane: (1) product runtime agents, (2) MCP external agent hosts, (3) engineering multi-agent (Andie). Mixing the three in support tickets creates confusion.

4. Augmented LLM pattern (canonical product pattern)

Aryx deliberately does not give small models free-form tool-calling over the graph. From graph/retrieve.py: local models are unreliable at free-form tools, so deterministic retrieval runs first; the LLM only interprets and writes prose.

Augmented Ask (product): question → extract terms (deterministic) → gather entities (GraphReader) ← TOOL, not LLM → render_context(evidence) → LLM synthesise answer ← LLM sees packed context only → grounding/citations ← same structure, no drift → return {answer, usage, tools_called} Augmented Intent (CPQ): question + session + candidate bundles (built deterministically) → pinned structured completion (JSON schema) → quarantine invalid variable_name / value_ref → dispatch to handlers OR clarify → handlers mutate CpqSession (not free LLM writes) → bom_gate before payload

3.2 Why this matters for SOP

  • Provenance: evidence structure is shared by answer + grounding — cannot diverge.
  • Safety: LLM never invents item_value for BOM; catalogs only.
  • Debuggability: tools_called and graph retrieve logs show tool path; LLM is step 4.

4.4 Engineering hub: Andie (Raven)

From agent-chaining skill: orchestrator decides what / order / who; specialists do work. Subagents get no parent memory — prompts must be self-contained. Parallel specialists (security · db · api) → hub synthesizes.

7. Peer-to-peer & blackboard (what exists / what does not)

Honest SOP answer: Aryx does not run a peer mesh of autonomous agents negotiating over a message bus (no A2A protocol, no agent-to-agent RPC fabric).

6.1 What looks like “peer” but is blackboard

  • Postgres blackboard: multiple modules read/write entities, adjudication, jobs without calling each other.
  • FalkorDB projection: readers (Ask, UI) peer-consume graph writes produced by project stage.
  • CpqSession client echo: browser and server pass state as message payload (turn-based), not agent mesh.

6.2 Shadow / dual-control (paired judgment)

Closest to “two agents disagree”: intent shadow mode runs LLM route + deterministic auditor; deterministic still decides; divergence logs at WARN. That is paired control, not peer negotiation. 

LLM route ──┐
            ├── log agreement ──► det path executes (shadow)
Det auditor ┘
llm_first: LLM path executes (with escape hatch)

6.3 When you would introduce real P2P

Only if product requires concurrent specialist negotiation (e.g. pricing agent ↔ compliance agent). Today: keep hub-spoke; use Raven agent-chaining skill for design reviews before building a mesh.

16. Operator SOP — common scenarios

S1 — “Which agent answered this Ask?”
  1. Inspect response tools_called and whether session_data.mode==cpq.
  2. If CPQ: take session_data.run_id, grep logs.
  3. If standard Ask: look for retrieve/gather + answer model in usage / llm_recent.
S2 — “MCP agent did something wrong”
  1. Identify tool name from host transcript.
  2. If act: check pending executions — may not have been approved.
  3. If ask: treat as normal Ask/CPQ debug with workspace_id from args.
  4. Check MCP token scope and ARYX_MCP_DEFAULT_WORKSPACE.
S3 — “Discovery agent mapped garbage types”
  1. Confirm Brief quality (vague brief → generic types).
  2. Check whether heuristic fallback fired in logs.
  3. Do not confirm map; edit types; re-run discovery if needed.
S4 — “Multi-agent engineering change broke prod”
  1. This is Raven plane — check git PR, not customer MCP.
  2. Run make cpq-regression; inspect CPQ-REG-* lines.
  3. Rollback via git; do not “fix” via MCP act in prod without approval chain.
