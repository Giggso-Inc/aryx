1. What Aryx is

Aryx is a knowledge-graph platform that ingests records from databases and documents, resolves duplicates into golden entities, projects a queryable graph, and answers natural-language questions with grounded citations. For CPQ / radio product catalogs it also runs a guided configuration conversation that ends in a validated BOM JSON payload — never free-text invented line items.

Core principle

Postgres is source of truth. FalkorDB is a rebuildable projection. Cheap deterministic stages shrink work so frontier LLMs only touch hard decisions (~1–5%).

Three surfaces

shay_backend identity & tenancy · aryx API graph / CPQ / ingest · apps/web Next.js UI

Isolation unit

Workspace — LIST-partitioned data, own graph, ontology, survivorship policy, Ask history, CPQ catalogs.

Contract boundary: apps/web is replaceable. The shared contract is FastAPI JSON + MCP. Do not put product logic only in React.

4. SSO & authentication

Product identity lives in Shay. Aryx also has a separate API-key middleware for service-to-service and MCP bearer access.

Shay identity shay_backend

Google / Microsoft SSO, email+password, email verification, JWT access + refresh, domain companies, invitations, password reset.

routes/sso.py · routes/auth.py · routes/user_auth.py · services/sso_service.py · middleware/auth_middleware.py

Aryx API key api/security.py

Modes: off / optional / required. Fail-closed: any exception in _bearer_ok → reject (DEC-006). Used for server-to-server and MCP tokens.

4.1 SSO flow (Google / Microsoft)

1. SPA POST /api/v1/sso/initiate?provider=google|microsoft (credentials: 'include' — sets SSO CSRF cookie) ← { authorization_url, state } 2. Browser → IdP login / consent 3. IdP → callback with code + state Shay verifies: · state matches · CSRF cookie present (same host — localhost ≠ 127.0.0.1) · redirect_uri allow-listed → exchange code for profile (email) → resolve/create user + company (domain or invite) → issue JWT access + refresh 4. SPA stores tokens; subsequent calls: Authorization: Bearer <access>

8. Ingest & discovery

Converts messy sources into landed records, proposed types, golden entities, and a graph projection.

8.1 Seven pipeline stages

#StageWhat happensCost
1ExtractStream DB connector or file readerI/O
2LandRaw record + provenance in PostgresPG write
3TagSemantic field labels (email, phone, currency…)Cheap LLM
4MapSource → entity type; HITL approval gateFrontier
5ResolveBlock → score → adjudicate → cluster → goldenMix
6RelateFK, co-occurrence, optional LLM edgesMix
7ProjectEntities + edges → FalkorDBGraph write

Stage checkpoints (StageTracker / checkpoint_store) allow resume from last completed stage. Crashed “running” stages treated as failed on resume.

8.2 Path A — Database

  1. Context / Brief — crisp domain sentence or context file.
  2. Connect & introspect — RDBMS host/port/db/user/password → schema list.
  3. Run discovery agent — tables → proposed entity types + match keys.
  4. Review & ingest — edit types, untick tables, start job; poll progress.

UI: DatabaseTab, DbConnectForm, DbReviewTables. APIs: connect_api, rest_ingest_api / admin ingest DB, jobs_api.

8.3 Path B — Documents

  1. Provide context (text or file).
  2. Upload files: JSON, CSV, PDF, PPTX, DOCX, images (limits: typically 50 files, ~2 MB each).
  3. Read & discover — extract text, propose entity types.
  4. Confirm types → add to graph.

UI: DocsTab, DocsUploadStep, DocsSummaryStep. APIs: file_ingest_api, doc_discover_api.

8.4 Path C — REST sources

Preview remote JSON, then ingest pages. UI: RestTab / RestConfigForm. API: /ingest/rest/preview, /ingest/rest/ingest.

8.5 CPQ XML catalogs (BigMachines-style)

9. Entity resolution funnel

LANDED RECORDS │ ▼ BLOCK MultiKeyBlocker (prefix + token-set + Soundex, size cap) │ candidate pairs ▼ SCORE cheap LLM pairwise similarity [0, 1] │ ▼ ROUTE four-band adjudication │ ≥0.92 AUTO_MERGE │ 0.90–0.92 frontier LLM adjudicate │ 0.75–0.90 human review queue │ <0.75 REJECT ▼ CLUSTER transitive closure · confidence = min merge-edge (clamp 0.5–0.99) │ ▼ GOLDEN RECORD survivorship (5 strategies + per-attr overrides + conflict audit)

Key files: resolution/run.py, blocking.py, survivorship.py, golden.py, confidence.py, chunked.py, review_queue.py, api/adjudication_api.py.

Chunked ER activates above ARYX_ER_CHUNK_THRESHOLD (default ~100k) — 3-pass streaming; memory ≈ largest block.

Adjudication HITL

  • GET /adjudication?status=pending — pair side-by-side
  • POST /adjudication/{id}/decide — approve | reject
  • Decisions persist as labeled training data

12. Ask module (full detail)

Entry: POST /ask → run_ask() in api/ask_api.py. Client sends question, optional history[] (role/text), workspace_id, and CPQ session_data (client-echoed state).

12.1 Top-level routing (Prompt 3 inverted router)

Config: ARYX_CPQ_INTENT_MODE = shadow (default) | llm_first | deterministic_first.

run_ask(req) │ ├─ live session_data.mode == "cpq"? ──YES──► _run_cpq_turn (engine owns state) │ ├─ hard_off_topic(question)? ──YES──► standard graph Ask (N10, no LLM) │ ├─ mode == deterministic_first? │ det is_cpq_question OR soft_quote OR legacy LLM gate │ YES → CPQ · NO → standard Ask │ ├─ classify_ask_route() [one structured Gemini call, timeout default 10s] │ routes: quote | qa | ambiguous | off_topic │ mark_top_level_route_used() // N4: skip mid-session 2nd LLM same turn │ ├─ timeout/error escape hatch → det OR soft_quote → CPQ else standard │ ├─ shadow: det/soft decide; log agreement at WARN on disagree │ └─ llm_first: execute route quote → _run_cpq_turn qa → _handle_cpq_qa (read-only product context; no silent family switch) ambiguous → clarifying question only off_topic → standard Ask

12.2 Standard Ask (graph Q&A)

  1. Extract terms / types from graph catalog
  2. gather entities + provenance
  3. render_context → LLM synthesise answer
  4. Grounding / citations (ask/grounding.py, ask/evidence.py)
  5. Optional scope checks
  6. Persist history / thread stores

Modules: graph/retrieve.py, ask/*, llm_runtime.py, broker/*, ask_history_api, ask_thread_api, ask_overview.

12.3 Session contract

  • CPQ state is client-echoed via session_data (no mandatory server session store).
  • run_id minted once; tags all cpq: logs via logging_context.
  • Ask history is separate multi-turn chat context; mined when CPQ starts after a non-CPQ turn (country residual Bug A fix).
  • Response may return updated session_data for the client to store and resend.

13. CPQ guided quote (conversation engine)

Package: src/aryx/cpq/. Driven by _run_cpq_turn in ask_api.py. Reads catalog attributes/rules from Postgres + graph; never invents item_values for BOM.

13.1 Eight conceptual steps

StepNameBehavior
1AnchorsProduct family + destination country (latched from NL / history)
2Load catalogload_product_config → ConfigAttr + options
3Rule loophide → recommend → constrain → auto_fill to fixed point
4PromptNext pending attribute (menu or type-exact if >25 options)
5Lock & loopApply answer; re-enter rule loop
6Review / cascadeChange requests, multi-intent, product switch snapshots
7Q&A pauseGraph questions mid-config; resume without losing filled
8Approval → BOMConfirm → bom_gate → build_payload JSON

13.2 Hardware-based product order (mandatory HW)

On catalogs with Hardware Version (hWVersion_* / label “Hardware Version”): Product (~325 options) is deferred until Hardware is filled. Pending rank: country/region → Hardware → other attrs → Product last.
Country (once, latched) │ ▼ Hardware Version (mandatory always-ask; never blind fill) │ constraints narrow portfolio ▼ Other config attrs (service, housing, battery, …) │ ▼ Product / productSelectionProduct_all (only after HW) │ ▼ awaiting_approval → confirm → bom_gate → payload

13.3 Country-once + history mine

  • Extract country from current question, product_anchor_question, switch trigger.
  • History mine: last ~8 user turns when CPQ starts after standard Ask (residual Bug A).
  • Keep longer order utterance when user later only types a short catalog name (e.g. aSTRO25_bom).
  • Do not re-ask country if already latched.

13.5 Replacement phrasings (wanted only)

Change replies like “use Premium instead of Standard” and the reverse “instead of Standard, prefer Premium” are split by extract_replacement_clause before apply_answer. Only the wanted fragment is matched; the rejected option is excluded via constrained values so fuzzy match cannot re-pick it. Log line: cpq_replacement:. Regression: N53–N57 + dialogue D07; units in tests/test_cpq_replacement_clause.py. Deep dive: Explorer · Agents SOP §12.

13.6 Multi-product session

product_snapshots (cap ~5) on switch A→B→A; switch confirmation gates; country re-validation when needed. N3 loop-exit: affirmative answers to pending switch questions stay inside _run_cpq_turn.

13.7 BOM invariants (non-negotiable)

  • Payload only from build_payload after rule loop + user confirm.
  • bom_gate must pass (constraints + provenance).
  • No free-text LLM invention of item_value.
  • Display uses human labels; API codes stay internal unless user types them as refs.

20.4 End-to-end CPQ happy path (SE demo script)

  1. SSO / login → open workspace with CPQ catalog ingested.
  2. Ask: full order sentence with country (and optional customer/qty).
  3. System latches country; asks Hardware Version (not Product first).
  4. User answers HW + remaining prompts; rules auto-fill safe defaults.
  5. Optional mid-config Q&A (“what are the options for …”) without killing session.
  6. Optional change (“change hardware”) → constrained menu.
  7. Summary → user confirms → bom_gate → BOM JSON returned.

21. How to plug in a feature (checklist)

Use this when explaining extension points or scoping new work.

  1. Surface? Shay (identity/tenancy) · Aryx API · web UI · MCP · Streamlit. Prefer API+tests first.
  2. Workspace scoped? Pass/validate workspace_id; use partitioned stores.
  3. Auth? Shay JWT for product users; API key middleware for services/MCP.
  4. Data writes? Postgres first; call projection if entities/edges change.
  5. Discovery / Brief? If new source type, wire connector + brief fields; keep HITL map gate.
  6. Ask extension? Prefer handlers as executors; extend intent_schema carefully; keep escape hatch + soft_quote.
  7. CPQ extension? Never invent item_value; use options / user source; BOM only via build_payload + bom_gate; respect HW-before-product ordering.
  8. MCP? Add tool spec + dispatch; wrap REST; document in CLAUDE_MCP_CONFIG.
  9. Observability? run_id / raven_log / LLM call table / job stages.
  10. Tests? Unit + offline regression row (append-only P##/N## for CPQ).
  11. Manifest? New libraries → .raven/manifest.json approval before commit.
  12. Docs? Link from this guide or FEATURES.md; keep architecture.md if structure changes.
Anti-patterns: free-text BOM fields from LLM; silent product-family switch; re-asking country after history already named it; asking Product (325) before Hardware on hardware catalogs; putting auth-only logic in the React client; writing to FalkorDB without Postgres.
