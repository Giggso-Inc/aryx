VERIFIED CONFIGURATION FINDING
This deployment overrides the ingestion safety caps
Code defaults: ARYX_XML_MAX_ENTITY_TYPES=20, ARYX_XML_MAX_ROWS_PER_TYPE=500.
This repo's .env: ARYX_XML_MAX_ENTITY_TYPES=50, ARYX_XML_MAX_ROWS_PER_TYPE=1200000.
  • With the code's own defaults: 11 of the 31 types (ranks 21–31 above, including bm_catalog and bm_prd_family) would be silently dropped entirely, and 12 of the 14 CPQ-relevant types (rules, rule inputs/actions, layout data) would be truncated to their first 500 rows.
  • With the actual deployed settings: nothing is lost — all 46,500 rows survive intact.
VERIFIED FINDING
bm_catalog / bm_prd_family aren't what drives product detection
Both are tiny (3 and 1 rows) and carry no usable name field. "APX Next" product detection actually resolves from the catalog_prefix ("ApxNextConfig") derived from the source filename, combined with real option data inside bm_config_attr/bm_menu_item — confirmed live: the system correctly resolves aPXNext_BOM regardless.

PHASE 1 — POST /admin/docs/read

HTTP HANDLER
Upload accepted, job scheduled
  1. Read file bytes, check 50 MB per-file limit — 23.8 MB passes
  2. discovery_id = uuid4().hex
  3. JobStore.create(discovery_id, "discovery", "APX_Next_config.xml", workspace_id) → INSERT aryx_jobs (status=queued)
  4. Schedule _read_job() as a background task
  5. Return {"discovery_id": "<hex>"} immediately — long before parsing finishes
§1.1
XML → CSV extraction (_xml_to_csvs)
  1. Parse the XML tree
  2. Recursively walk it: an element counts as a real "entity" only if it has 2+ distinct non-container child tags, or (if childless) at least one attribute of its own
  3. Bucket every matching element by tag name, count occurrences
  4. Apply the two caps (see the warning above — both are overridden in this deployment, so nothing is dropped or truncated for this file)
  5. One CSV produced per surviving type — e.g. APX_Next_config_bm_config_attr.csv (427 rows), APX_Next_config_bm_config_rule.csv (688 rows)
Plain English: Aryx reads the whole file, recognizes 31 distinct "kinds of things" inside it, and — because this deployment raised the normal safety caps — keeps every one of the 46,500 rows intact for review.
§1.2
Per-type extraction pipeline
For each of the 31 CSVs: schema inference, FK-column detection (columns ending "_id" matched against other types' own id/guid columns), entity-mention extraction. All still in-memory/preview — nothing hits aryx_entity yet.
RESULT
GET /admin/docs/summary/{discovery_id}
Returns the full preview: 31 discovered types, row counts, inferred FK relationships (e.g. bm_config_rule_input.bm_config_rule_id → bm_config_rule.id).

PHASE 2 — POST /admin/docs/confirm

ENTRY
All 31 discovered types approved
ingest_confirmed() → run_pipeline() → resolve_run(). For each approved type, an aryx_entity row is created per real record:
ontology_type = SourceFilePrefix + PascalCase(tag)
e.g. "APX_Next_config" → prefix "ApxNextConfig" → bm_config_attr becomes "ApxNextConfigBmConfigAttr". This prefix is exactly the catalog_prefix the CPQ engine later uses to scope every query to just this one export.
§2.1
Entity resolution
427 bm_config_attr rows → 427 real aryx_entity rows (native BM id preserved, e.g. id=39427001 for the "commerceAttrs" field). Exact-ID fast path (ARYX_ER_EXACT_ID_MATCH, default on) skips full resolution when the native id already matches an existing entity.
§2.2
FK / relationship detection
Two passes: within this confirm batch, and against ontology types from earlier confirms in the same workspace. Concretely: bm_config_rule_input.bm_config_rule_id → bm_config_rule.id (1,694 edges), bm_config_layout_attr_assoc.attr_id → bm_config_attr.id (1,001 edges), and every other real FK-shaped column across all 31 types.
§2.3
Golden-record survivorship + isolated-node safety net
Per-workspace merge policy (default "most_complete") reconciles duplicates. _relate_isolated() runs unconditionally afterward — any entity with zero relationships gets a best-effort fallback edge.
§2.4
Graph projection + zero-loss validation
project_graph()/project_incremental() mirrors the new rows into FalkorDB. Post-ingest validation confirms row-count parity — this run: 46,500 in, 46,500 projected, 0 lost.
Plain English: every one of the 46,500 discovered rows becomes a real, permanent, correctly-linked database record, scoped so this catalog's data can never collide with a different product's data in the same workspace.

PHASE 3 — POST /ask (CPQ conversation)

TURN 1
"Quote APX Next Enhanced radios for a US customer." (workspace_id=14)
Step 1 — Anchor gate: product detected against real catalog_prefix "ApxNextConfig" instantly; country hint "for a US customer" → "United States" — both anchors satisfied in this one message (confirmed live: this exact scenario resolves in a single turn).

Step 2 — Load configuration: all 427 ApxNextConfigBmConfigAttr entities loaded, product resolves to "aPXNext_BOM". Hiding/recommendation/constraint rules drawn from 688 real rules; BML evaluator loads all 923 script bodies.

Step 3 — Rule loop: using the real 1,694 condition clauses and 1,007 action outcomes, "Hardware Version = Enhanced" + "Country = US" together satisfy enough real rules that every remaining field resolves automatically — Region→NA, Frequency Bands→700/800 MHz, Housing→Black, Battery Type→Standard, Solution Type→RadioCentral + CPS Programming, and ~45 more real decisions.
RESULT
pending is EMPTY after just this one message
Status → awaiting_approval. Plain-English summary of ~50 real decisions shown; JSON only on request.
TURN 2
"confirm"
Status → approved. build_payload() emits the real BOM JSON — variable_name → item_value for every resolved field. Noise/system fields (company-level currency/language/number-format, _BM_-prefixed, CRM_-prefixed) excluded from the payload.
Plain English: by the time a customer's opening sentence gives just two real facts (product + country), the 688 real rules already ingested from this exact file are enough to resolve an entire APX Next radio order automatically.
