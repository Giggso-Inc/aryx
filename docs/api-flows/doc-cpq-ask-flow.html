POST /ask — CPQ Guided-Configuration Flow

src/aryx/api/ask_api.py :: _run_cpq_turn() — one turn of a multi-turn quote-building conversation. See doc-cpq-ask-flow.md for the fully detailed, step-by-step reference.
STEP 0
Restore session + product-switch confirmation
Rehydrate CpqSession from session_data, or start fresh. If the previous turn asked "switch products and discard progress?" — this turn's text is that yes/no answer, handled before anything else.
Plain English: the whole conversation's memory travels in session_data — there's no server-side session store.
STEP 1
Sequential anchor gate — product, then country
  • Product unknown → detect from real ingested catalog names, or ask and STOP
  • Product known, different one mentioned → ask to confirm switch, STOP
  • Country unknown → ask, STOP
early return until both known
STEP 2
Load the product's configuration attributes
load_product_config() → every field, its menu options, defaults, hidden/required flags. Loads this catalog's hiding / recommendation / constraint rules and the BML script evaluator.
visible_attrs, hiding_rules, rec_rules, con_rules, bml_eval
ROUTER
status == "awaiting_approval" ?
If the quote already finished a full pass with nothing left pending, every turn from here routes through the review-stage checks (JSON preview → approval → Q&A → change/cascade → re-show summary) instead of the configuring loop below.
STEP 5
Lock in the answer to last turn's question
Match this turn's text (or the earlier hint) against the pending field's real options. No match + real options exist → re-show the question, STOP. Decision-required siblings (country/region-shaped) inherit the same value.
STEP 3
Rule-evaluation loop — hide → fill → recommend → constrain
Repeats up to 8 passes until nothing changes:
  • Hide — apply hiding rules, drop stale answers for newly-hidden fields
  • Auto-fill — hint → default → single-remaining-option; never guesses a real 2+-option decision
  • Recommend — rule-driven "if A=X then B=Y" fills
  • Constrain — narrow which options remain valid
filled, display_filled, constrained_opts, pending
pending EMPTY
STEP 6 — Completion
status → awaiting_approval. Plain-English summary only — never raw JSON here.
turn ≥ MAX_TURNS
Turn-cap safety valve
Never fabricates a finished BOM. Explicitly says incomplete, keeps asking.
normal case
STEP 4 — Ask one field
"json"/"batch" request → preview / full list. Otherwise: context sentence + next pending field's real options.
RETURN
Every branch converges here
{ answer, session_data (echoed back by client next turn), cpq_payload (only on final approval), preview }

Side branches (triggered from the review-stage router or mid-configuration)

STEP 6b
Cascade (change request)
Erase changed field + everything depending on it → lock in new value → re-run Step 3's rule loop → log every value that actually changed.
STEP 7
Contextual Q&A
Answers a genuine question from the graph without touching configuration state, then resumes exactly where the conversation left off.
STEP 8
Approval → BOM payload
Only on an explicit "confirm" — builds and returns the real order payload. Preview mode never sets cpq_payload.
