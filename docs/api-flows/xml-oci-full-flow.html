XML File · OCI Mode — /read → /confirm Full Flow

XML is structured data (DATA_EXTS), not a document — it bypasses the document pipeline entirely. OCI Document Understanding is never called. Every LLM chat + embed call re-checks the OCI settings on every single call and routes to OCI GenAI when OCI mode is on — no matter which broker object made the call. In full OCI mode the relational tables (aryx_runs, aryx_landed, aryx_entity, …) are Oracle ADB 23ai tables too, not Postgres — reached through a shared connection-pool + SQL-translation layer, not just the final graph-projection step.

Read this first — the mechanism behind every "OCI" badge on this page
"OCI Mode" is not one switch — it's several independent settings that happen to default together
Setting ARYX_OCI_MODE=true is a convenience toggle (settings._resolve() in config.py): every per-service backend field (parse_backend, embed_backend, llm_cheap_backend, llm_frontier_backend, db_backend, graph_backend) defaults to "oci" unless you explicitly set that one field to something else. Four separate "effective_*_backend()" checks then decide, independently, whether each concern talks to OCI:
1
Chat calls (aryx/llm.py: complete_text() / complete_json()) call _use_oci_for(tier) on every single call, before even looking at the Broker's model registry. If effective_llm_cheap_backend() or effective_llm_frontier_backend() says "oci", the call short-circuits straight to OCI GenAI (Cohere Command R / R+) — this is why even the "local-looking" broker built for /read and /confirm (_local_broker() in admin_api.py, registered with provider="ollama") still ends up calling OCI once OCI mode is on. It is a global settings check, not a broker property.
2
Embed calls (Broker.embed() in broker/__init__.py) do the same thing for effective_embed_backend() — same mechanism, same "checked fresh on every call, independent of the broker instance" behaviour.
3
Relational-store calls (every PostgresStore / EntityStore / OntologyStore / DatasourceStore / JobStore write in Phases 1 and 2 of this flow) go through get_pool(dsn) (store/pool.py), which checks effective_db_backend() and swaps the whole connection pool from psycopg3 to OraclePool (store/oracle_pool.py, python-oracledb-backed). This is the part the old version of this page never mentioned — it only described the OCI switch for the final graph write.
4
Graph calls (Stage 5, below) check effective_graph_backend() directly inside orchestrate.py:run_pipeline() and construct an OracleGraphStore using settings.oci_adb_dsn — a different setting from the one the relational stores use (see the DSN note below).
⚠ DSN split worth knowing: the relational stores above are constructed with settings.rdb_dsn (env ARYX_RDB_DSN) everywhere in this flow — never settings.effective_dsn() or settings.oci_adb_dsn. get_pool() only decides which driver to use (psycopg vs. oracledb) from effective_db_backend(); it still hands that driver the literal string in ARYX_RDB_DSN. So a real OCI deployment must point ARYX_RDB_DSN itself at the Oracle connect descriptor — ARYX_OCI_ADB_DSN is a second, separate setting used only by the Stage 5 graph store (and a few other call sites that explicitly call effective_dsn(), such as main.py's stale-job sweep). The two values are not automatically kept in sync by the code.
Once the pool is Oracle, queries.load(name) (queries/__init__.py) prefers a hand-written override in queries/oracle/<name>.sql when one exists, otherwise passes the ordinary Postgres-flavoured SQL through a regex translator (_translate_sql in oracle_pool.py) that rewrites %s/%(name)s placeholders to :1/:name, drops ::jsonb/::text casts, turns RETURNING col into an out-bound RETURNING col INTO :out, rewrites LIMIT n OFFSET m into OFFSET m ROWS FETCH NEXT n ROWS ONLY, and converts ON CONFLICT DO NOTHING into "catch Oracle's ORA-00001 unique-violation error and swallow it." Parameter values are translated too — Python bool → 'Y'/'N' (Oracle has no native boolean column), psycopg.Json() wrappers → plain JSON strings for CLOB columns, empty strings → a single space (Oracle treats '' as NULL).
Plain English: think of it less as "XML goes to Postgres, then a copy gets pushed to Oracle" and more as "every store class always writes the same logical rows — but in OCI mode, a thin compatibility shim rewrites the SQL on the way out so it lands on Oracle instead of Postgres, transparently, without the calling code knowing the difference."

Local XML Parser — doc_discovery.py:_xml_to_csvs()
XML → one CSV per detected entity element type
Parses with defusedxml.ElementTree (safe against XML bombs/billion-laughs attacks). If the file fails to parse, or if no element in the whole tree qualifies as an "entity" (see below), the function gives up and returns the raw, untouched bytes as a single opaque CSV named {stem}.csv — nothing is invented, and nothing crashes the job.
Six sub-steps inside one function call
1
Decide what counts as an "entity" — an XML element qualifies only if either (a) it has ≥ 2 distinct child-element tag names (a multi-field record), or (b) it has no children at all but ≥ 1 XML attribute (a self-closing leaf like <Widget id="1" name="alpha"/>). An element with exactly one child tag name and some attributes qualifies as neither — this single rule is the most common reason a real-world XML file yields fewer CSVs than someone expects.
2
Skip transparent containers — tags starting with _ (e.g. <_children>) and ISO locale codes used as multilingual value wrappers (en, de, fr, ja_JP, and 20+ others, including bare 2-letter Oracle CPQ/BigMachines codes) are walked through, not counted as entity types themselves — their real children inherit the FK lineage as if the wrapper weren't there. <script>/<style>/<head> content is skipped outright.
3
Extract fields from both XML attributes and child-element text. For a multilingual field (a child with locale sub-children), the <en> value is preferred; otherwise the first non-empty locale value is used.
4
Auto-fill a name field when a row has no name — checked against a priority list of candidate fields (variable_name, label, file_name … plus CPQ/BigMachines-specific hints like bm_variable_name, func_name, rule_name, java_class_name that degrade gracefully to no-ops on non-CPQ data).
5
Inject the FK column — every entity row gets a {parent_tag}_id column set to its nearest non-container ancestor's id/guid. This is how _detect_fk_links() later finds the relationship automatically. If the parent has no id/guid at all, no FK column is injected for its direct children (deliberately — a constant placeholder value would create a spurious column that can never be joined).
6
Rank, cap, and write CSVs — of all qualifying entity types, those with a real name field are preferred over unnamed ones (typically pure junction/FK-only tables), ordered by frequency, and the list is capped at ARYX_XML_MAX_ENTITY_TYPES (default 20, not a fixed "top 3"). Each type's row count is separately capped at ARYX_XML_MAX_ROWS_PER_TYPE (default 500). One CSV per surviving type is written as {stem}_{tag}.csv.
Worked example — an XML shape that actually clears the entity-classification bar in step 1:
<catalog>
  <product id="P1" name="Widget A">
    <price>9.99</price>
    <category id="C1" name="Widgets"/>
  </product>
  <product id="P2" name="Widget B">
    <price>14.99</price>
    <category id="C1" name="Widgets"/>
  </product>
</catalog>
Why this shape and not a simpler one: <product> has two distinct child tag names (price, category) so it clears rule (a); <category> has no children but does have attributes, so it clears rule (b). Verified by running _xml_to_csvs() against this exact input:

Ingest loop — run_pipeline() called once per approved file, non-last files in parallel
This is not a plain "for file in files" loop. All non-last approved files run concurrently in a thread pool sized by ARYX_INGEST_WORKERS (default 3); only the single last file then runs afterward, serially. Two reasons: the last file's FK links (Stage 4 below) need every entity from every earlier file to already exist, and only one process may safely rebuild the graph projection at a time (non-last files pass skip_graph=True). With exactly two files, as in this example, the practical effect looks like "product runs, then category runs" — but the mechanism is parallel-then-serial, and with three or more approved files the first N-1 genuinely race each other.

Stage 3 / 6 — Relate (last file only, and OFF by default)
LLM Relationship Inference → aryx_relationship
⚠ Two gates, not one: run_pipeline(..., relate=is_last and settings.ingest_relate). Both must be true for this stage to run at all: (1) it must be the last approved file — it never runs twice for a two-file batch — and (2) ARYX_INGEST_RELATE must be set to true; it defaults to false because large payloads (e.g. CPQ function bodies embedded in some XML exports) have been observed to make this stage hang. Stage 5 / 6 — Relate Isolated safety net (× 2 files, always runs)
_relate_isolated() — the actual "no orphan nodes" guarantee
Not present in earlier versions of this page, and — unlike Stages 3/3.5 — not gated by ARYX_INGEST_RELATE. Every run_pipeline() call ends with this stage. It finds every entity in the whole workspace with zero relationship edges (one anti-join query, not a per-entity scan), groups them by ontology type, and makes one LLM call per isolated type — not per isolated entity — using a single sample anchor from another type. If that call says the types are related, one edge is created from every isolated entity of that type to the anchor. Needs at least 2 distinct ontology types already resolved to do anything, so it is a no-op the first time it runs (only CatalogProduct exists yet) and does its real work the second time (after CatalogCategory is also resolved).
Plain English: this is the safety net that makes the earlier "Relate" stage optional in the first place — even with ARYX_INGEST_RELATE=false, no entity is left completely disconnected from the graph; it just gets connected by this cheaper, type-level pass instead of the more expensive per-pair one.
aryx_relationship INSERT (only if ≥ 2 types + isolated entities exist) OCI GenAI Chat (frontier) — always runs, cost bounded by type count not entity count

This page was compared line-by-line against the current source (doc_discover_api.py, doc_discovery.py, orchestrate.py, config.py, store/pool.py, store/oracle_pool.py, queries/__init__.py, broker/__init__.py, llm.py, llm_runtime.py, source_catalog.py) and one claim was additionally verified by executing _xml_to_csvs() directly against a test payload rather than trusting a source-code read alone.

XML worked example The example XML (<product> with attributes id/name/price and one nested <category> child) produces catalog_product.csv + catalog_category.csv. Running _xml_to_csvs() against that exact XML today returns one raw-upload CSV (catalog.csv containing the untouched XML bytes) — the log line is literally "no entity elements detected … falling back to raw upload." A <product> with exactly one child tag type does not clear the current entity classification rule. The flagship example no longer demonstrates what it claims to. Replaced with an XML shape (product has two child tags: price + category) that was confirmed by execution to produce the expected two-CSV output.
Entity-type cap "top-3 tags appearing ≥ 2 times" Structural rule per element (≥2 distinct child tag types, or a childless leaf with ≥1 attribute), capped at ARYX_XML_MAX_ENTITY_TYPES (default 20), named types preferred over unnamed, rows per type separately capped at ARYX_XML_MAX_ROWS_PER_TYPE (default 500). "Top 3" undersells real CPQ/ERP exports with 15-20 element types by an order of magnitude, and the classification rule — not a frequency count — is what actually decides whether something becomes an entity at all.
Missing step Not mentioned. _persist_xml_sources() writes the original XML + derived CSVs to aryx_datasource before FK detection. Without this, a reader would not know the original uploaded file is retrievable later — only the derived CSVs were described as persisted.
Missing step Not mentioned. _detect_fk_links_workspace() links the last file to ontology types already in the workspace, not just to other files in the same batch. Explains how a single later XML upload still gets linked into an existing graph — the old page implied FK detection only ever compared files within one confirm call.
Relate stage gating "Stage 3/5 — Relate (× 2 files, relate=True)" — implied it always runs, once per file. relate=is_last and settings.ingest_relate — runs at most once (last file only) and ARYX_INGEST_RELATE defaults to false. Out of the box this stage does not run at all for tabular/XML ingests. This was the single most misleading claim about "every run" OCI chat usage — the OCI Chat (frontier) relate call is opt-in and rare in practice, not routine.
Missing step Not mentioned. _infer_schema_fk_links() ("schema_fk" stage) — one LLM call across all type schemas, gated the same as Relate. Rounds out the picture of what "relate=True" actually turns on.
Missing step Not mentioned. _relate_isolated() — always runs (no settings gate), one LLM call per isolated ontology type, guarantees no fully disconnected entity. This is the actual "zero orphan nodes" guarantee, and it is unconditional — omitting it made the gated Relate stage look load-bearing when it is actually optional enrichment.
Ingest loop shape "Loop — run_pipeline() called twice" (implied a plain sequential loop). Non-last files run concurrently in a thread pool (ARYX_INGEST_WORKERS, default 3); only the last file runs serially afterward. Correct for 2 files by coincidence; matters once 3+ files are approved in one batch.
Scope of "OCI Mode" Only Stage 5 (graph projection) was described as switching to Oracle; Stages 1-4 were shown with Postgres-flavoured detail ("payload JSONB"). ARYX_OCI_MODE=true also flips effective_db_backend() to "oci" by the same convenience-toggle mechanism, which swaps every relational store's connection pool (psycopg3 → oracledb) and runs all SQL through a translation shim — this affects aryx_runs, aryx_landed, aryx_entity, aryx_relationship, aryx_datasource, aryx_jobs, everything, not only the graph write. This was the biggest gap relative to the page's own title — "OCI Mode" was really only documented for one of its six-plus effects.
DSN split Not mentioned — implied one DSN setting drives OCI mode. Relational stores use settings.rdb_dsn (ARYX_RDB_DSN) everywhere in this flow; the graph store uses settings.oci_adb_dsn (ARYX_OCI_ADB_DSN) instead. The two are separate settings that a deployment must set consistently itself. Operationally important: setting only ARYX_OCI_ADB_DSN and leaving ARYX_RDB_DSN at its Postgres default would not move the relational tables to Oracle.
HTTP validation claim "Validates: ≤50 MB · extension in DOC_EXTS ∪ DATA_EXTS" at the /read handler. The handler only checks the 50 MB size limit. Extension filtering happens later, silently, inside _read_job() — a file whose extension is in neither set is dropped with no error surfaced anywhere. A user uploading an unsupported file type gets no feedback that it was ignored.
