# CPQ Hardcode Audit — dev_oci

Branch `dev_oci` at commit `803845fe` — CPQ engine and API
25 September 2026 · Verification pass by Claude Code, mapping the 11 themes from `docs/CPQ_Hardcode_Audit_Solutions_Impact.docx` (audit of `dev-rv-msi`@`0b448e42`, 24 September 2026, prepared by Swathi Arasu) onto `dev_oci`'s independently-evolved codebase.

**Bottom line: every one of the 11 themes from the original audit is still substantially present in `dev_oci`, and a second, open-ended pass beyond those 11 themes found more — including the single most severe findings in this entire document.** The engine has no per-catalog role map, no per-model policy store, no shared constants module, and the `workspace_id` default-to-1 pattern — has grown to **95 occurrences** across `cpq/`+`api/` alone. But the fresh, unconstrained pass (see "Fresh findings" below) surfaced something worse: a **verified SSRF bypass** in the platform's own guard, an **unauthenticated database-connection endpoint**, and a **cross-tenant endpoint with no workspace scoping at all** whose bulk-archive action can wipe every tenant's job history in one unauthenticated call. Those three outrank everything in the original 11 themes for urgency. A handful of real, independent improvements exist alongside all of this — a proper ISO-3166 country-validation layer, a genuinely DB-enforced read-only graph-query mode, a tighter multi-select opt-out allowlist, a deliberate hardware-version anchor redesign — but none of them touch the structural root cause any of the 11 themes describe. `dev_oci` did not inherit `dev-rv-msi`'s specific commit history (they share a July 22 common ancestor and diverged independently since), so this is not "the same bug, still unfixed" in the literal sense — it is the same *pattern* of hardcoding, re-derived independently on a sibling branch, which is itself informative: catalog-specific literals keep reappearing in this codebase regardless of which branch writes them.

## Scope, method and limitations

**Scope:** `src/aryx/cpq/` and `src/aryx/api/` only, matching the original audit's scope. `shay_backend` and `apps/web` were not audited (same as original).

**Method:** this is a *verification* pass, not a from-scratch independent audit. Six parallel read-only research agents each took 1-2 of the original's 11 themes and searched `dev_oci`'s actual current code — by identifier name and by behavior, not by trusting the original's line numbers — because `dev_oci`'s `cpq/` was split from 19 files (dev-rv-msi) into **291 files** during this repo's "Raven Style Compliance Plan" refactor (`engine.py` alone went from 14,800+ lines to 2,328); `api/` similarly grew from 34 to **255 files**. Every finding below cites a real `dev_oci` file:line, verified by an agent actually reading that code, not inferred from the old document.

**What this method cannot catch:** genuinely new `dev_oci`-only hardcoding that has no analogue in the original audit's 11 themes. This is a targeted verification of known issue *patterns*, not an unconstrained fresh audit. A handful of sub-claims in T10 (exact decline-vocabulary/source-tag-set counts) were not exhaustively re-verified — flagged as UNCERTAIN below rather than assumed, per the reviewing agent's own honesty about effort budget.

**Structural facts, confirmed via git:**
- `dev_oci` and `dev-rv-msi` share a common ancestor at `452304e9` (22 July 2026) and have evolved independently since.
- `dev-rv-msi`'s audited commit `0b448e42` (#362) is **not** an ancestor of `dev_oci` — its specific bug-fix lineage (and the new bug it introduced) never reached `dev_oci`.
- `dev_oci`'s `cpq/` = 291 `.py` files / `api/` = 255 `.py` files, vs. the original audit's 19 / 34.

## What's different from the original audit — genuine findings, not just re-confirmations

**Got worse, not better:**
- `workspace_id: int = 1` — **95 occurrences** in `dev_oci`'s `cpq/`+`api/` alone (`cpq`: 7, `api`: 88), vs. the original's "110 occurrences repo-wide." `CpqSession` still has no `workspace_id` field. This is the platform's highest-confirmed-severity finding in both audits, and it has not shrunk.
- T10's predicted failure mode — "no single source of truth, so values drift independently" — has a **confirmed live instance**: `dev_oci` now has *two* region-code lists that have diverged from each other (`_COUNTRY_TO_REGION` has 5 codes including "ME"; `_REGION_PATTERNS` has only 4, missing "ME" entirely). This isn't a re-confirmation of the original's list — it's new evidence the predicted drift mechanism is actively happening.

**Genuinely improved:**
- **Country validation**: a real ISO-3166 alias system (`country/country_alias_data*.py`, 249 countries, pycountry-derived) now exists — this fixes country *recognition*, though the separate region-*derivation* table (`_COUNTRY_TO_REGION`) was carried over unchanged and still has the original's bugs.
- **Cypher "read-only" endpoint**: now uses FalkorDB's actual server-enforced `GRAPH.RO_QUERY` mode, not just a regex keyword blacklist — a real fix for that specific endpoint. (No live Oracle Graph equivalent exists to have the same risk, since Oracle Graph exposes no raw-query endpoint at all.)
- **Hardware Version anchor (T3)**: a deliberate design decision (documented "D1") removed HW from the anchor-blocking chain entirely — "Product held back until HW filled" no longer applies. The specific *new* high-risk bug the original audit found in commit #362 (`_attrs_confirmed_not_applicable_for_hint`, drops pending questions for models with no sequence rows) does not exist in `dev_oci` at all — that fix lineage never merged here.
- **Optional multi-select opt-out (T7)**: narrowed from a blanket rule to a hard 3-item allowlist, each individually verified.
- **Decline-side yes/no parsing (T8)**: hardened to a word-boundary regex, with an explicit code comment citing the exact "swallows real country names" bug it guards against — but this fix was **not mirrored to the affirmative/yes side**, which is still naive prefix matching (`reply.startswith(("y","yes",...))`), so "you know what, keep this one" still misparses as yes.
- **Boolean type-guard (T5)** and **unvalidated-country-on-switch (T5)**: both fixed with explicit guards.

Neither of these categories changes the top-line conclusion: the structural root causes (no per-catalog profile, no per-model policy, no shared constants module, dangerous default parameters) are all still present.

## Per-theme findings

### T1 — Catalog variable names used as universal keys

**Problem (verified in dev_oci — PRESENT, relocated):** All originally-named literals are present: `modelSelectionbaseModel_astro`, `modelSelectionRegion_astro`, `productSelectionProduct_all` (~36+ sites, matching the original's estimate), `hiddenMasterStringForAstroPortable_astro`, `_DECISION_ANCHOR_VNS` — spread across ~15-20 new files instead of one `engine.py`. SVX's `modelSelectionBaseModel_viSoln`/`modelSelectionRegion_viSoln` are still **never referenced anywhere** — zero hits, exact match to the original's claim. One nuance the original didn't note: dev_oci's *fragment*-based checks (matching substrings like "basemodel") would actually catch SVX's names too, since they lowercase to `...basemodel...` — only the exact-literal paths are truly SVX-blind. Evidence: `src/aryx/cpq/fill_signature.py:39-42` (`_DECISION_ANCHOR_VNS`), `hiding_rules/data_table_forced.py:73`, `data_table_bridge/attr_governance.py:51`, `api/ask_stale_constraint/ask_invalidate_stale_base_model.py:12`.

**Root cause:** the engine has no per-catalog map of which variable plays which role, so the APX NEXT names seen live were written in directly. Every data-table helper exits quietly when the base model is empty, so other catalogs fail silently. Unchanged in dev_oci.

**Fix (per original design):** a `CatalogProfile` per workspace and catalog, naming the product, model selector, base model, region, country, hardware-version and master-string variables, resolved in order from (1) the catalog's own `attrToVarMapping` table, (2) overlap between an attribute's option values and data-table columns, (3) layout plus whole-token name matching, (4) today's literal where it exists (keeps APX NEXT identical), (5) otherwise none, with a warning. Replace every literal with `profile.<role>`; roll out in shadow mode, APX first, SVX last. **Not started in dev_oci** — no `CatalogProfile`-equivalent mechanism was found anywhere in the codebase.

**Impact (in dev_oci today):** every SVX quote still runs without data-table narrowing and suppression; APX 3000/900 keep stale hidden values, unchanged from the original finding.

**Phase 3 scoping (2026-09-25):** ground-truthed the above against current code before writing anything. Actual blast radius is larger on a raw literal count than this section's estimate (125 sites/50 files across the 5 named literals, driven mostly by `productSelectionProduct_all`'s use as a plain `filled`-dict key in 40 of those files) — but priority (1) of the fix design above **already exists and works**: `resolve_variable_name_for_role()` (`data_table/data_table_product.py`) already resolves a human role label to its real per-model variable name via the ingested `attrToVarMapping` Data Table, catalog-agnostic, tested, live-verified against real APX1000 data — it simply has exactly one caller today (`search_products_by_feature`, NL product search), never wired into any of the quote-engine hot paths that still read the 5 literals directly. The remaining 3 role-resolution literals, `productSelectionProduct_all`'s 40-file dict-key usage, and the actual `CatalogProfile` object unifying all of this are still not started — this was one shadow-log-only pilot site, not a completed rollout.

Wired into `payload_building/anchor_exclusions.py::_data_table_resolved_anchor_vns()` (a pure-read, single-file, already-narrow config_data-only helper — not one of the two Region-reading sites embedded in larger `compute_data_table_setup`-style control flow), placed right after the function's existing `product`-empty guard so the check only ever runs when the function would have proceeded anyway. Same gating (`catalog_profile_shadow_check_enabled`, off by default), same never-raises contract. 3 new tests (flag off = not called, flag on = called with exact args, no-product guard still short-circuits before the check). Regression-checked: the file's own 8 existing tests plus 97 tests across 3 more cascade-adjacent integration files, all passing. Remaining T1 work unchanged from the note above, minus this one literal.

**Phase 3 — the actual CatalogProfile class (2026-09-25):** the pilot slices above shipped a free function, `shadow_check_role_vn()`, that independently re-resolved CPQ model candidates on every call — adequate for two separately-gated call sites, but not the real design ("a `CatalogProfile` per workspace and catalog..."). ### T2 — APX NEXT fallback model and data-table conventions

**Problem (verified — PRESENT):** `_DEFAULT_CPQ_MODEL_CANDIDATES = ("APXNEXT", "APXNEXT_BOM")` present verbatim, now duplicated in *two* places (`engine.py:587` and `data_table_bridge/candidates.py:15`) — a new instance of the T10 drift pattern. Region lookup still reads only ALLOW rows, no DISALLOW handling (`data_table/data_table_product.py:17-77`, repeated at line 347). `catalog_prefix` being ignored is now **self-documented in a code comment** as intentional/unaddressed (`data_table/data_table_loader.py:87-92`). Stale-model markers (`btadelete`, `_po-`, `-del`, `-remove`) present verbatim. The renamed "Basemodeltoconfig" loader (now `resolve_product_hint()`) still does an unbounded per-prefix workspace scan per call.

**Root cause:** no explicit "unknown model" result, no schema contract for data tables, no catalog ownership of tables, and no allow/deny model. Unchanged.

**Fix (per original design):** return an empty result plus a logged data gap instead of APX NEXT, behind a flag; treat DISALLOW rows as vetoes and re-validate an already-filled Base Model; normalise column names at load time with an alias table; stamp each table with its catalog at ingest and filter by catalog at load time; replace stale-code patterns with an active-model registry; cache the loaders. **Partially started in dev_oci**: the separate `_load_all_tables` path gained a 300s TTL cache (addresses the "rescans every call" performance concern for that one function), but none of the correctness fixes (DISALLOW veto, catalog stamping, unknown-model result) exist anywhere.

**Impact (in dev_oci today):** unmapped products can still get an APX NEXT Base Model or APX NEXT legal values; a country-banned Base Model can still be filled; `resolve_product_hint()` still scans the whole workspace per call (call frequency not independently traced end-to-end — flagged uncertain by the reviewing agent, but the unbounded-scan code shape itself is confirmed).

**Phase 1 fix applied (2026-09-25):** the DISALLOW-veto piece is done — `resolve_region_allow_value()` (`data_table/data_table_product.py`) now tracks DISALLOW rows at the same model/region(/country)/attribute scope and returns `None` (never guesses) instead of the otherwise-matching ALLOW value when one exists. Narrow and additive: only suppresses the specific value a DISALLOW row names, at the scope it names — zero effect when no DISALLOW rows exist, so every pre-existing ALLOW-only caller/test is unaffected. 3 new tests (veto fires, veto is scope-limited to its own model, country/region vetoes stay independent), all passing alongside the 3 pre-existing tests. The rest of T2 (empty-result-behind-a-flag, catalog stamping at ingest, active-model registry) is still not started.

**Phase 1 follow-up (real-data testing against workspace 704, 2026-09-25) — found and partially fixed a severe latency bug, unrelated to correctness.** Attempted to validate the DISALLOW veto against the exact real scenario this function's own docstring cites ("confirmed live 2026-08-10: APXNEXTSINGLE/region=NA resolves modelSelectionbaseModel_astro to H45TGT9PW8AN") — that specific ALLOW row doesn't exist in workspace 704's current data (correctly returned `None`, not a bug), but the call itself took **411 seconds**. Root cause: `_load_all_tables()` (the shared loader both this function and `resolve_variable_name_for_role()`'s `_load_attr_var_mapping_rows()` sit on top of) looped `list_ontology_types()` (109 distinct types on this workspace) and issued one `fetch_entities_by_exact_type()` RDB round trip per type — the same N+1-round-trip shape as the `ask_overview`/`observability_api` finding under T11 item 8, just in the CPQ data-table layer instead of the graph layer. **Partial fix applied:** new `fetch_all_entities_grouped_by_type()` on both `PostgresCpqRdb`/`OracleCpqRdb` replaces the per-type loop with one query; both call sites updated. Re-measured live: 411s → 265s (~35% faster) for the identical call — a real, structural improvement (109 round trips → 1), but **not a full fix**: the remaining ~265s is dominated by `fetchall()` itself (confirmed via direct profiling: connection+execute together took under 3s, `fetchall()` alone took 265s materializing 299,388 rows' full JSON `attributes` blobs), and raising the cursor's `arraysize` from 500 to 10,000 barely moved it (265s → 239s), ruling out fetch-batch-count as the remaining bottleneck. The likely remaining cause — Oracle's native `JSON` column type possibly forcing per-row LOB reads, or genuine data-volume/bandwidth limits for ~300K rows of JSON over this link — needs Oracle-side visibility (LOB storage thresholds, actual network throughput to this ADB instance) this pass didn't have, or a larger redesign (server-side shape-filtering via JSON predicates instead of fetching every row's full attributes and classifying in Python, which risks the catalog-agnostic shape-detection design this function is built around). Flagged as still a real, severe production risk (a live customer's first CPQ turn against this workspace after a 5-minute gap would still face a 265s+ stall) rather than closed. 7 test-double (`_FakeRdb`/`_FakeSequenceRdb`/`MagicMock`) definitions across 7 test files updated to implement the new method — the pre-existing per-type-call-counting tests (`test_attr_ever_governed_for_cpq_model_reuses_cache_across_many_attrs`, `test_module_cache_survives_a_60s_gap_between_calls`) now assert one grouped call instead of one call per ingested type, which is itself a small independent confirmation the consolidation works as intended.

### T3 — Hardware Version and the product anchor sentence

**Problem (verified — mixed):** Tier A still marks HW mandatory with no applicability check (`mandatory_input.py:135-141`). HW hint tokens (5G/LTE/4G + two APX NEXT labels) present verbatim (`engine.py:216-219`). The "device sentence never reset on product switch" bug is **confirmed still present**: `session.product_anchor_question` is a plain `str` (`state/__init__.py:332`), and `_complete_product_switch` resets several session fields but never touches this one.

**Root cause:** the session has no structured record of which device is being quoted; HW applicability was attached to a free-text sentence, not to the resolved product. Partially addressed (see Fix), partially unchanged.

**Fix (per original design):** store a structured anchor (text, resolved CPQ models, turn); one helper replaces the three rules, reset on product switch; decide HW applicability as yes/no/unknown from the filled product, not a free-text sentence; use a HW hint only when exactly one option matches; seed Product only when the anchor's models match. **Genuinely done, in part, via a different route than proposed:** dev_oci made a documented design decision ("D1") removing HW from the anchor-blocking chain entirely, rather than building the proposed structured-anchor object — "Product held back until HW filled" no longer applies at all. But the free-text `product_anchor_question` itself is still unstructured and still never resets on switch, so the underlying root cause (no structured anchor) stands for that specific field. Separately: the *new* bug the original audit found in `dev-rv-msi` commit #362 (`_attrs_confirmed_not_applicable_for_hint`, which drops pending questions for devices the sequence data doesn't mention) **does not exist in dev_oci at all** — that fix lineage never merged here, so this specific new-bug risk doesn't apply.

**Impact (in dev_oci today):** HW is no longer force-ordered ahead of Product (the original's worst-case symptom is gone), but Tier A can still mark HW mandatory without checking applicability, and a stale `product_anchor_question` from before a product switch is still read by downstream code without being reset.

**Phase 1 fix applied (2026-09-25):** `_complete_product_switch()` (`ask_turn_switch/ask_turn_product_switch_complete.py`) now resets `session.product_anchor_question = ""` alongside the other pending-* fields it already clears. `_seed_product_select_from_anchor()` tries the stale anchor text as a fallback seed candidate ranked *above* the already-confirmed new `product_name` — removing it removes a wrong-match risk, not a real signal (`pending_switch_question` already carries this switch's own triggering text correctly). 1 new regression test, passing. Tier A's missing HW-applicability check is still not started.

### T4 — Empty-value list and value filters

**Problem (verified — PRESENT, one claim not reproduced):** `_NONE_VALUES` present, exactly 16 values (`engine.py:68-72`), used across 25+ files. The "test"/"dummy"/"pager" substring filters are genuine substring (`in`) checks, not exact matches — "LATEST RELEASE" still matches "test" via "LA-**TEST**" (`region_and_noise_constants.py:58-60`). 6. **Arbitrary SQLite file access via `/admin/connect`** — PRESENT, `connect_api.py:53-61`, no path restriction on a `dialect="sqlite"` request. **Phase 2 — partially addressed:** the unauthenticated-access half of this is closed (see New theme A item 2 below) — `/admin/connect` now requires `require_api_key` fail-closed regardless of `ARYX_API_AUTH` mode, so an anonymous caller can no longer use this endpoint to probe the filesystem at all. The arbitrary-path itself, for an *authenticated* admin, is left as-is: "connect to any database including a local SQLite file" is the endpoint's stated feature, and restricting it to a safe base directory is a product decision (which directory? configurable how?) this pass didn't make unilaterally.
7. **Read-only query enforcement** — MIXED, net *better* than the original finding. The surviving FalkorDB Cypher endpoint now uses real DB-enforced `GRAPH.RO_QUERY`, not just a regex blacklist. No equivalent raw-query endpoint exists for Oracle Graph at all.
8. **Hardcoded 500-record cap silently truncating counts** — PRESENT, `ask_overview.py:34`, same pattern also independently in `observability_api.py:50`. **Phase 2 fix applied (2026-09-25):** new `count_entities(ontology_type=None)` added to both `GraphReader` (FalkorDB, `count(e)` Cypher) and `OracleGraphReader` (`COUNT(*)` SQL) — a true, uncapped count instead of `len(find_entities(limit=500))`. `ask_overview.py`'s `_kinds()` now derives its type list from `distinct_types()` (already deterministic/unsampled) and a true per-type count instead of grouping a single capped scan; `observability_api.py`'s `_graph_stats()` calls the new total-count method directly. 11 new tests across 3 files, all passing.

   **Phase 2 follow-up (real-data testing against workspace 704, 2026-09-25) — the first fix above was correct but not production-safe as shipped.** Real-data validation against workspace 704 (109 distinct entity types, 204,491 entities, real dev_oci Oracle backend) surfaced a latency regression the mocked unit tests couldn't catch: `_kinds()`'s `distinct_types()` + one `count_entities(t)`/`find_entities(ontology_type=t, limit=3)` pair *per type* measured at **~276s** for this workspace (~2.5s/type × 109 types). `ask_overview.build()` runs on every non-quote `/ask` turn (confirmed by tracing `ask_thread_api.py::submit_message()` → `run_ask()` → `_standard_ask_pipeline()` for the off-topic/QA-fallback/cold-start-not-a-quote branches; live CPQ quote turns skip it via `_route_quote()`), so this would have added ~4.5 minutes to every such turn in production. Fixed by replacing the per-type loop with one grouped query: new `type_overview(sample_limit=3) -> {type: {count, samples}}` on both backends — a single `WITH e.type, count(e), collect(e.name)[0..N]` Cypher query for FalkorDB, two queries (one `GROUP BY type` count, one `ROW_NUMBER() OVER (PARTITION BY type ...)` windowed-top-N-per-group query) for Oracle, replacing up to 218 round trips with 1–2. Re-validated against the same real workspace 704: `type_overview()` now completes in **3.53s** for all 109 types (78x faster), `ask_overview.build()` end-to-end in 4.16s, and the sum of per-type counts still equals the independently-verified true total (204,491) — correctness preserved, not traded for speed. 9 more tests across 2 files, all passing.

**Root cause:** no explicit "unknown workspace" result (client-supplied default fills the gap with workspace 1); no single auth-required setting; SSRF/read-only guards implemented as pattern-matching instead of using the platform's actual safety primitives (DNS resolution, DB-enforced read-only mode). Unchanged for 6 of 8 claims.

**Fix (per original design):** a shared FastAPI dependency that requires the workspace or derives it from the caller's token; one auth setting defaulting to required, refusing to start with auth off outside development; reject placeholder/short API keys; resolve DNS in the SSRF guard and block internal ranges/service names; remove free-form database URLs; use `GRAPH.RO_QUERY` for the Cypher endpoint (**done**); one `GROUP BY` count for overview counts instead of a hardcoded cap. **One of seven concrete sub-fixes done** (the RO_QUERY enforcement); the rest — required workspace, one auth default, key validation, DNS-resolving SSRF guard, database-URL restriction, unbounded overview counts — are all unaddressed.

**Impact (in dev_oci today):** a client that omits `workspace_id` can still act on workspace 1's data, including deletes, across 88 API call sites; a deployment copied from `.env.example` still starts with auth effectively off; the shared placeholder key would still authenticate against a real deployment that hadn't rotated it; internal service names are still reachable through the SSRF-guarded ingest/share paths.

## Fresh findings — beyond the original 11 themes

The verification pass above answers "does the same pattern `dev-rv-msi` found still exist in `dev_oci`." It cannot, by construction, catch hardcoding that has no analogue in that document. To close that gap, six further parallel research agents did an open-ended sweep of the same `cpq/`+`api/` trees, organized by code area rather than by theme, each told explicitly what was already documented so they'd hunt for genuinely new ground. They found a lot — including the three most severe findings in this entire report.

### New theme A — API authorization gaps beyond T11 (the most urgent findings in this report)

1. **HIGH — Verified SSRF bypass via IPv4-mapped IPv6 literals.** `src/aryx/api/ssrf_guard.py:21-51`: `BLOCKED_HOSTS`/`PRIVATE_NETS` never account for IPv4-mapped IPv6 addresses. `ipaddress.ip_address("::ffff:169.254.169.254") in ipaddress.ip_network("169.254.0.0/16")` returns `False` — a cross-version comparison that silently fails rather than raising — so `http://[::ffff:169.254.169.254]/` (the cloud metadata service) sails through unblocked, as does `::ffff:127.0.0.1` and `::ffff:10.x.x.x`. This was verified by direct execution, not inferred. Reachable via `rest_ingest_api.py` and `share_config_api.py`'s `endpoint_url`/`extra_headers` validators, both of which call `check_outbound_url` directly. This is a distinct bug from the already-documented "SSRF guard doesn't resolve DNS" finding — a different bypass vector in the same guard. **Phase 2 fix applied (2026-09-25):** `check_outbound_url()` now unwraps an IPv4-mapped `IPv6Address` (via `.ipv4_mapped`) to its underlying `IPv4Address` before the `PRIVATE_NETS` membership check, so the same blocklist catches both forms. 3 new parametrized regression tests (IMDS/loopback/RFC-1918 via `::ffff:` literals), all passing; all 20 pre-existing `test_ssrf_guard.py` tests still pass unchanged, including the one documenting DNS resolution as intentionally out of scope (see T11 item 5's Phase 2 note).
2. **HIGH — `/admin/connect`, `/admin/discover`, `/admin/ingest/multi` have zero authentication.** `src/aryx/api/connect_api.py:96-133`. Unlike their siblings in `admin_api.py`/`ontology_api.py`, these three routes carry no `require_api_key`/`write_api_key` dependency. `/admin/connect` builds a live database connection string from fully caller-supplied `host`/`port`/`dialect`/`user`/`password` and immediately calls `test_connection()` + `introspect()` — an internal-network database-port probe with no per-route auth fallback if the global `ARYX_API_AUTH` middleware is ever `optional`/`off` (which `.env.example` ships as its default, per the already-documented T11 finding). **Phase 2 fix applied (2026-09-25):** all three routes now carry `Depends(require_api_key)` — the same hard, fail-closed-regardless-of-mode dependency `admin_api.py::rebuild_graph` already used — matching the sibling-router pattern this finding says was missing. 4 new tests (`tests/test_connect_api.py`, no prior test coverage existed for this router at all): each route 401s with no/invalid key, and a valid key clears the auth gate (proven by reaching the downstream connection-failure path, not a mocked bypass).
3. **HIGH — `jobs_api.py` has no workspace scoping at all — cross-tenant IDOR, plus an unauthenticated global data-wipe.** `src/aryx/api/jobs_api.py:27-93`. `get_job`, `get_job_events`, `cancel_job`, `resume_job` take only a `job_id` — `JobStore.get()`/`events()`/`finish()` (`src/aryx/store/job_store.py:49-77`) never filter by workspace, so any caller who can reach these routes can view, cancel, or resume another workspace's job. Worse: `POST /admin/jobs/archive` (line 96, `days: int = 30`, no `workspace_id` parameter) calls `JobStore.archive_old()` (`job_store.py:79-91`), which purges finished jobs and their events **globally, across every workspace** — one call, with no auth dependency on any route in this file, can delete every tenant's ingestion history and audit trail.
4. **MEDIUM — Auth hardening is inconsistent across `api/` routers, making the global middleware config a single point of failure.** Only `admin_api.py` (partially), `ontology_api.py`, `shay_bridge_api.py`, and `mcp_tokens_api.py` use the route-level fail-closed auth dependency. Everything else — `data_api.py`, `actions_api.py`, `rules_api.py`, `axioms_api.py`, `relationship_type_api.py`, `workspace_api.py`, `connect_api.py`, `datasource_api.py`, `graph_api.py` (including the arbitrary read-Cypher endpoint), `jobs_api.py`, the ingest subdirectories, and half a dozen more — has zero per-route defense-in-depth and relies entirely on the global middleware. If that middleware is ever misconfigured (which the shipped `.env.example` already demonstrates is possible), essentially the whole admin/data-mutation surface opens at once.
5. **MEDIUM — `admin_api.py` is internally inconsistent.** `get_entity`, `ingest_db` (triggers a full background ingest pipeline), and `list_runs` lack the same `write_api_key`/`require_api_key` dependency that `create_entity`/`update_entity`/`delete_entity`/`rebuild_graph` received in the same file — looks like an incomplete retrofit of an auth-hardening pass, in the one file that otherwise shows the team knows how to do this correctly.
6. **LOW — Hardcoded file-size limits sized for one specific customer's export.** `src/aryx/api/file_ingest/file_ingest_limits.py:14-21`: 500MB/file, 1.5GB/total, 50 files — the code's own comment says these were bumped to fit one real MSI catalog file (`aSTRO25_ConfigData.xml`, 223MB) at an operator's explicit request. Not environment/settings-configurable.
7. **OBSERVED, NOT YET INVESTIGATED — `/admin/observability` intermittently returns silently-wrong `{"entities": 0, "relationships": 0}` under load, unrelated to the T11 item 8 fix above.** Surfaced 2026-09-25 while re-validating the `type_overview()` fix against the live dev_oci container (workspace 704): repeated calls to `GET /admin/observability?workspace_id=704` alternated between hanging past 15-40s with no response and returning in ~2s with `graph: {entities: 0, relationships: 0}` — while a direct in-process call to the exact same `count_entities()`/`type_overview()` on the exact same running container consistently returned the correct `204491` in 2-4s. `observability_api.py::observability()` calls `_job_summary()`/`_llm_stats()`/`_recent_llm()` (a separate RDB-backed Oracle pool) *before* `_graph_stats()`, and `_graph_stats()`'s own `except Exception: return {"entities": 0, "relationships": 0}` (unchanged by this session's fix — see T11 item 8) would silently swallow any real error from pool contention/timeout without logging it. Root cause not yet isolated — could be pool exhaustion under concurrent load, a race in shared pool state, or something specific to this dev container's Oracle connectivity (this environment has known prior Oracle connection instability, per earlier session work on cursor arraysize tuning). Flagged here rather than chased immediately since it sits in code this session didn't touch and reproducing it reliably needs dedicated load-testing, not ad hoc curl calls against a shared dev instance.
8. **FIXED — `/admin/graph/rebuild` was hardcoded to `FalkorStore`, a real no-op on this OCI/Oracle Graph deployment.** `src/aryx/api/admin_api.py::rebuild_graph()` always constructed `FalkorStore(settings.graph_url, ws_graph(workspace_id))` and rebuilt that graph, regardless of `ARYX_GRAPH_BACKEND`. Confirmed live 2026-09-25: this deployment's `get_settings().effective_graph_backend()` returns `"oci_graph"` (verified via `ports().graph_reader(704)` resolving to `OracleGraphReader`), so every prior call to this endpoint silently rebuilt an unused FalkorDB graph while leaving the real Oracle graph tables (and the RDB/graph sync gap surfaced above) completely untouched — same "assume FalkorDB everywhere" root cause as several other T11/New-theme-A findings, just not one the original 8-claim checklist named. **Fix applied (2026-09-25):** mirrors `orchestrate.py`'s own `effective_graph_backend() == "oci_graph"` dispatch — constructs `OracleGraphStore(settings.oci_adb_dsn, workspace_id)` (lazy-imported, raising a clear `503` instead of a silent no-op if the OCI extras aren't installed) when the backend is `oci_graph`, `FalkorStore` otherwise. 3 new tests (`tests/test_admin_api.py`) covering both branches plus the missing-dependency 503 path, all passing alongside the 3 pre-existing tests. Verified against the real container: the fixed endpoint correctly issued `DELETE`/`INSERT` statements against `aryx_graph_vertex`/`aryx_graph_edge`/`aryx_graph_provenance` (confirmed via `aryx.graph.oracle_graph_store` log lines) rather than touching FalkorDB at all. The rebuild itself was not carried to completion in this session (stopped mid-run at the user's request, safely — see the workflow note below) — the sync gap in item 7's sibling finding (299,388 RDB entities vs. 204,491 graph nodes) remains open, but the endpoint that would close it is now confirmed to target the correct backend.

### New theme D — Silent truncation and unbounded caps with no signal to anyone

- **HIGH — an unpaginated `limit=200` fetch, repeated across 4 call sites, for a model tree another part of this same codebase documents as exceeding 325 entries.** `nl_hint_extraction/model_leaves.py:39,79`, `model_path.py:53`, `ingested_products.py:101,106` all fetch a catalog's `BmCatalog` tree capped at 200 (or 50, for one entity type) rows with no pagination loop and no truncation check. `turn_intent/next_question_helpers.py:37` independently documents that one real catalog's model selector "carries the full ~325-model portfolio" — meaning this cap is already confirmed too small for at least one real catalog, silently dropping models from leaf-detection, path validation, and alias-map building.

Any catalog whose mandatory-attribute set genuinely needs more than 5 real back-and-forth turns to resolve gets truncated mid-configuration regardless of how many real questions remain unanswered.

## Recommended priority

Nothing here should be read as "safe to defer" — but if forced to sequence:

**1. New theme A first, ahead of everything else, including T11.** The SSRF bypass, the unauthenticated `/admin/connect`, and `jobs_api.py`'s missing workspace scoping (especially the unauthenticated global archive-wipe) are the only findings in this whole report with direct, unauthenticated, cross-tenant-data impact rather than a dangerous-default that still requires the caller to supply a real workspace ID. They're also small, independent, mechanical fixes — add the existing `require_api_key`/`write_api_key` dependency to three more files, filter `JobStore` by workspace, normalize IPv4-mapped-IPv6 before the SSRF guard's range check. No catalog-modeling work required.

**2. T11's original findings next** — same shape of fix, same urgency class, already scoped by the original audit. T9's `workspace_id` count (95, confirmed growing) makes the case concrete rather than theoretical.

**3. New theme D's two HIGH findings** (`MAX_TURNS=5`, the unpaginated 200-row model-tree fetch) — both correctness bugs with a **confirmed** real-world trigger already documented elsewhere in the same codebase (a catalog with a ~325-model portfolio, exceeding the 200-row cap outright). Worth fixing before more catalogs onboard, not after.

**4. T1/T2/T6 plus new theme B** (the catalog-profile and per-model-policy root causes, now with ~9 more confirmed call sites of the same literal-as-universal-key pattern outside the original audit's scope) — the largest and most interconnected work. Needs the structural `CatalogProfile`/`ModelPolicy` fix, not more allowlist patching.

**5. New theme C's duplicated-logic findings** — worth fixing opportunistically (each is a small, isolated diff) but lower urgency than the above, since two of the three are fail-safe (fall back to default behavior) rather than fail-open.

## Caveats

- This report combines two passes: a verification pass against a specific, named prior audit's 11 themes, and a separate open-ended sweep for hardcoding outside those themes. Even combined, this is not an exhaustive security audit — it is bounded by six agents' research budgets across 546 files in one sitting. Issues neither pass happened to surface are not ruled out.
- No live database, Data Table CSV, or running deployment was used — all findings are static-code verification, same limitation the original audit disclosed for data-dependent effects. The SSRF bypass is the one exception: it was verified by direct Python execution of the actual guard function, not just read.
- T10's decline-vocabulary/source-tag-set/product-selector-test sub-claims were not exhaustively re-verified against every one of `dev_oci`'s 291 cpq files; the confirmed instances (hint-length drift, region-list drift, noise-var split, "@@@" duplication, "(none)" scatter, plus new theme C's `_WEAK_SOURCES` finding) are presented as representative evidence for the theme, not a complete enumeration.
- The "Fresh findings" section's six research agents were each given an explicit list of already-documented patterns to avoid re-reporting; some overlap or near-duplication with the 11-theme findings may still exist despite that instruction, since "materially different variant" judgment calls aren't perfectly consistent across independent agents.
- `shay_backend` and `apps/web` remain out of scope, matching the original audit.
