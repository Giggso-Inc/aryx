## ISSUE-003 — `undo` never reverts a plain single-attribute fill

**Severity:** Medium

**Problem:** Sending `undo` with nothing changed yet correctly reports "nothing to undo." But after a genuine single attribute fill (e.g. answering the Hardware Version question), `undo` again returns the identical "nothing to undo" message instead of reverting the fill. Reproduced independently on workspaces 39004 and 39005 (test suite cases 30, and the original 39004 finding).

**Root cause:** `push_snapshot()` (`src/aryx/cpq/session_guard.py:65-78`) is the only writer to `session.history`; `restore_last_snapshot()` (`session_guard.py:81-101`) is the only reader. Every `push_snapshot(` call site in the codebase (exactly 5, all in `ask_api.py`, lines 1730, 1844, 1923, 3117, 5905) is a cascade/rule-conflict-reask path. The plain "answer a newly-asked pending question" path (`ask_api.py:9629-9716`) calls `_cpq_engine.apply_answer(...)` and directly mutates `session.filled[pending_var]` / `session.filled_multi[...]` — with **no `push_snapshot()` call anywhere in that block**. A fresh fill invalidates nothing, so it never reaches the cascade/reask functions that are the only places that snapshot.

**Fix:** Added `push_snapshot(session, reason="attr_fill")` immediately before the direct `session.filled[pending_var] = iv` / `session.filled_multi[pending_var] = ...` assignments in the STEP-5 pending-answer block (`ask_api.py`, current STEP-5 block ~9985-10000).

**Follow-up audit (2026-08-17, code-review remediation round):** every `_cpq_engine.apply_answer(`/`apply_multi_answer(` call site in `ask_api.py` was individually traced (line numbers shift with edits; current locations at time of audit: 1693, 2036, 3186, 8517, 8580, 9048, 9992-9998):
- **1693** (`_constrain_excluding_rejected`) — non-mutating: resolves a rejected value's normalized form to filter `attr.options`; never writes `session.filled`.
- **8580** (pending-answer-vs-switch disambiguation guard) — non-mutating: used only as a boolean probe (`bool(...)`) to decide answer-vs-switch precedence; result is never assigned into session state.
- **9048** (pending-change-value resolution) — mutates only a local `_pcnv_matched` boolean; on match it falls through to `return _handle_cascade(...)` (line 9078), which snapshots itself (see below) before ever touching `session.filled`.
- **2036** (inside `_handle_cascade`, def at line 1891) — real `session.filled` mutation, but `_handle_cascade` itself calls `push_snapshot(session, reason="cascade")` at line 1931, before this line runs. Covered.
- **3186** (inside `_handle_cascade_multi`, def at line 3103) — same pattern; `push_snapshot(session, reason="cascade_multi")` at line 3125 runs first. Covered.
- **8517** (product-anchor seed-from-text, first-time Product fill) — **was the one genuine gap**; no snapshot existed on this path. Fixed by adding `push_snapshot(session, reason="product_anchor_seed")` immediately before the `session.filled["productSelectionProduct_all"] = ...` assignment.
- **9992-9998** (STEP-5 pending-answer block) — the original fix above; snapshot now precedes both the single-select and multi-select assignment branches.

Audit closed: no remaining un-snapshotted `session.filled`/`session.filled_multi` mutation path through `apply_answer`/`apply_multi_answer`.

**Verification:** Re-run case 30 (`quote → undo [no-op] → fill Hardware Version → undo [should now revert]`).

## ISSUE-001 — country stated in a non-turn-1 quote message is never extracted

**Severity:** High

**Problem:** Turn 1: a QA-only question ("What countries do you support for APX NEXT?"), no quote started yet. Turn 2: "OK, give me a quote for APX NEXT in Germany" — explicitly states the destination country. Expected: `session.country` set to "Germany" from turn 2's own wording. Actual: the system re-asks "what's the destination country?", ignoring the country already stated in the same message. Re-verified as still-reproducing after pulling the latest `dev-rv` (commit `50d8522`), which included an unrelated country-name/code aliasing fix.

**Root cause:** `live_session = req.session_data.get('mode') == 'cpq'` (`ask_api.py:~10499`) is used as the discriminator for "is this an already-started, live quote session" — but `CpqSession.mode` defaults to the string `"cpq"` unconditionally (`state.py:297`), regardless of whether a product/quote was ever actually started. Turn 1's QA response echoes back a fresh `CpqSession().to_dict()` that already carries `mode: "cpq"` even though `product_name`/`filled` are empty. Turn 2 evaluates `live_session = True` from this stale field alone and routes straight to `_route_quote(req, reader)` **without ever calling `classify_ask_route()`** — the turn-1 unified LLM extraction that would have read "Germany" out of the message never runs. Confirmed via live docker logs: `"cpq_router: live_session product='' status='configuring' — skip top-level route"`.

**Fix:** Replace the `mode == 'cpq'` discriminator with a real quote-in-progress signal — `bool(session.product_name)` — so a session with no product ever selected is never treated as "live" for routing purposes. Audit other call sites currently trusting `mode == 'cpq'` as this same signal before changing it. Preserve the existing, already-correct turn-1 country-hint block (`ask_api.py:~7455-7484`) unchanged.

**Verification:** Re-run case 3 (QA turn → "quote for APX NEXT in Germany" should extract Germany immediately, no re-ask).

## ISSUE-004 — country-change chat confirmation desyncs from the actual quote payload

**Severity:** High

**Problem:** Customer sends explicit country-change requests (e.g. "change country to Germany"). The chat confirms it ("Country → Germany") and `session.country` updates correctly. But the underlying `filled` CPQ attributes — `CRM_BILL_COUNTRY`, `CRM_SHIP_COUNTRY`, `ultimateDestinationCountry`, `packageRegion` — remain stuck at the original country from initial quote load, even after multiple subsequent confirmed changes. Reproduced independently in two separate live sessions (cases 46, 49); one session's own config-review snapshot printed the stale values back verbatim right after a confirmed change.

**Root cause (two-layer):**
1. `_build_country_change_response()` (`ask_api.py:5449-5469`) does only `session.country = new_country; answer = f"Country → {session.country}"` and returns immediately — short-circuiting before the hint-extraction/cascade block (`ask_api.py:7438-7501`) that would normally re-derive country-shaped attrs.
2. Even on a later turn that does reach the cascade path, it flows into `auto_fill()`, whose docstring (`engine.py:4739`) states it "Only fills attrs that are not already filled. Does not override prior values." Since these attrs were already filled once at initial load, `auto_fill` never overwrites them on any subsequent turn either.

**Scope expansion (confirmed via live DB investigation, not speculative):** A follow-up question was raised — if country changes, should an already-filled `Product` that's no longer valid for the new country be cleared and re-asked? A read-only investigation against the live Postgres-backed rule tables (`aryx-postgres-1`) confirmed **yes, this is a real, active constraint today**, not a hypothetical:

- `Constraint Product based on region and Customer Type` (rule `17691443705`, active both workspaces) — disallows Product value "APX NEXT INTL FED" unless `ultimateDestinationCountry == "IL"` or `customerType == "FEDERAL"`.
- `Restrict Product Selection Attribute For Series Model` (rule `17691442921`, active both workspaces) — performs a real `country → region → util.getRestrictedCPQModels()` lookup that restricts which Product values are valid.
- `Restrict APX Next INTL unless testing customerUIN for LACR` (rule `17691443257`, active in 39005) — restricts Product value "APX NEXT INTL" by Region unless a specific test customer UIN is set.

"APX NEXT (International)" is a genuinely enforced, country-gated option — not a cosmetic label. The fix must therefore do more than re-sync 4 mirror fields.

**Fix (final scope):**
1. In `_build_country_change_response()`, after `session.country = new_country`, explicitly clear `CRM_BILL_COUNTRY` / `CRM_SHIP_COUNTRY` / `ultimateDestinationCountry` / `packageRegion` before re-running `auto_fill`, so the "don't override prior values" guard doesn't block the intentional re-derivation.
2. Additionally, re-invoke constraint-rule validation on `productSelectionProduct_all` (and any other attribute referenced by the three rules above) whenever country/region changes — if the currently-filled Product value is no longer valid under the new country, clear it and re-ask, mirroring how a direct Product change already invalidates ~80 downstream attributes today. This is scoped narrowly to the confirmed rule targets found above, **not** a blanket cascade retrofit of every attribute.

**Verification:** Re-run cases 46 and 49 (mirror-field sync); add a new case that changes country to/from a value that trips one of the 3 constraint rules above and confirms Product gets cleared and re-asked rather than silently retaining an invalid value.

## ISSUE-002 — explicit decline at `awaiting_approval` is misdispatched as an approval

**Severity:** High

**Problem:** After a session reaches `status=awaiting_approval`, sending an explicit, unambiguous rejection — "no, decline that" — produces `tools_called: ['cpq_payload_approved()']`, `status: post_approval`, and a full JSON BOM payload. An explicit decline is interpreted as a confirmation and the quote gets approved anyway. Reproduced live (case 25).

**Root cause:** The deterministic regex gate (`_APPROVAL_RE`, `engine.py:8428-8435`, via `detect_approval()` at `engine.py:8706-8708`, checked at `ask_api.py:8849`) correctly returns `False` for "no, decline that" — it is not the culprit. The turn falls through to the LLM-first universal classifier (`ask_api.py:9024`), which has three compounding gaps:
1. **No DECLINE category exists.** `intent_schema.py:37-83` enumerates every `IntentCategory` — there is no category representing an explicit rejection.
2. **APPROVAL is excluded from the deterministic cross-check.** `MUTATING_CATEGORIES` (`intent_gateway.py:55-63`) requires `_mutating_agrees` deterministic-detector agreement (lines 752-790) for every member except `APPROVAL`. Once the LLM emits `category="approval"`, it dispatches immediately (`intent_gateway.py:792-813`) with zero sanity check.
3. **The classification prompt gives the LLM no semantic guidance.** `_llm_classify_once`'s system prompt (`intent_gateway.py:305-321`) lists categories as a bare enum-value string, with no example distinguishing approval language from decline language.

Downstream, `_dispatch_intent_result`'s APPROVAL branch (`ask_api.py:5357-5367`) fires on `category == APPROVAL and confidence == HIGH` alone, calling `_handle_approval()` (`ask_api.py:5834`) directly.

**Fix:**
1. Add `IntentCategory.DECLINE` to `intent_schema.py`, with explicit negative-example guidance in the classification prompt (`intent_gateway.py:305-321`) — "no", "decline", "reject", "don't submit".
2. Add `APPROVAL` to `MUTATING_CATEGORIES` (`intent_gateway.py:55-63`) so it receives the same deterministic cross-check every other mutating category already requires — gate dispatch on `detect_approval()` agreement (or explicit absence of a hard negation).
3. Add a dedicated decline handler (mirroring `_handle_approval()`'s factoring) that returns the session to `configuring` rather than approving.

**Verification:** Re-run case 25's decline turn; add an isolated regression test for "no, decline that" sent while `status == awaiting_approval`.

## ISSUE-007 — country-name/abbreviation-punctuation variants fail across THREE independent extraction paths (all countries, not just US)

**Severity:** High
**Found:** manual live testing during this planning session (not part of the original 50-case suite). Scope expanded after a follow-up investigation traced every place country validation happens.

**Problem:** "US.A" (a real-world punctuation variant of "U.S.A") fails to resolve to United States. Initially reported on turn 1, but tracing the code showed this is not one bug — it's **three separate, independently-failing mechanisms**, each with its own extraction/validation logic and its own gap:

| # | Scenario | Mechanism | Fails on "US.A" today? |
|---|---|---|---|
| A | Turn 1, cold start ("quote for APX NEXT in US.A") | `classify_ask_route()` LLM call — `intent_gateway.py:992-1080` | **Yes** — LLM extraction miss |
| B | Bare reply to the "what's the destination country?" anchor question (customer just types "US.A") | Raw string passthrough — `ask_api.py:7453`: `hints["country"] = req.question.strip()` — no LLM call, no alias lookup, no punctuation cleanup at all | **Yes** — validated only against the old `_COUNTRY_TO_REGION` dict, which has no `"us.a"` key |
| C | Explicit "change country to US.A" mid-session | `detect_country_change_request()` regex (`engine.py:751-765`) as a GATE, then the real value comes from an already-existing LLM call, `_llm_confirm_and_extract_country()` → `gateway_classify_intent()` (`ask_api.py:4595-4649`, `7419-7433`) | **Works for this exact string, but only by luck of the gate** — the regex's `[A-Z]{2}` capture happens to truncate at "US" right before the period, which passes the gate's own `is_recognized_country()` check and lets the already-existing LLM call fire. The regex's captured value is explicitly *never used* as the country (`ask_api.py:7414`, "deliberately unused") — the LLM's own extraction is. But since the **gate itself** uses the same old narrow dict, most other variants never reach the LLM call at all. |

This is a general pattern risk, not a US-only quirk: any country whose common punctuation/abbreviation/colloquial variant isn't an exact match against the validation table is equally exposed (e.g. "U.K", "S. Korea", "U.A.E", "Ivory Coast" vs "Côte d'Ivoire") — in ALL THREE scenarios above, not just turn 1.

**Root cause (confirmed live and by code trace):**

- **Path A (turn 1):** Turn-1 country extraction is deliberately LLM-only by design (`docs/CPQ_COUNTRY_LLM_ONLY_PLAN_2026_08_13.md` — the old regex-rescan fallback was intentionally removed). The router LLM call correctly classifies the message as `route=quote`/`confidence=high` (confirmed via live docker logs: `llm_route=quote det_is_cpq=True agreement=True error='' timed_out=False`), but its structured `country` field comes back empty for "US.A" — a genuine entity-extraction miss, not a call failure. The system prompt's only country guidance (rule 5, `intent_gateway.py:~1043-1050`) covers unusual **sentence structure**, not punctuation/abbreviation normalization.
- **Path B (bare anchor reply):** `ask_api.py:7453` takes the customer's raw reply text verbatim as the country hint with zero normalization, then validates it via `is_recognized_country()` (`engine.py:6445-6466`), which checks membership in `_COUNTRY_TO_REGION` — a small, hand-typed dict of exact strings per country (`engine.py:1626-1649`), not the newer `_COUNTRY_ALIAS_GROUPS`.
- **Path C (change command):** `detect_country_change_request()` (`engine.py:751-765`) is a GATE, not the value source — its own docstring and the caller's comment (`ask_api.py:7409-7415`) are explicit that its captured text is "deliberately unused." When the gate returns non-None, the REAL value comes from an already-existing LLM call, `_llm_confirm_and_extract_country()` (`ask_api.py:4595-4649`), which calls `gateway_classify_intent()` and only accepts a `COUNTRY_CHANGE` result whose `country_text` passes `is_recognized_country()`. So Path C already has an LLM step doing exactly the kind of recognition ISSUE-007 needs — but the gate in front of it (`detect_country_change_request`'s own internal `is_recognized_country()` check on its regex capture) uses the SAME old narrow dict, and rejects most punctuation/abbreviation variants before the LLM call is ever reached. For "US.A" specifically the gate happens to pass (regex truncates to "US", which the old dict does recognize) — that's why this one case "works," coincidentally, while most others wouldn't.

**The unifying root cause:** the codebase already built the *right* data structure to solve this — `_COUNTRY_ALIAS_GROUPS` (`engine.py:404+`, 249 real ISO 3166-1 countries as symmetric alias groups: common name, official name, alpha-2, alpha-3, plus 13 manual colloquial supplements) — but it's wired into only **one** of the four places that validate a country string (`apply_answer`'s exact-whole-reply matching from commit `0381164`). `is_recognized_country()` is the single function relied on by Path B's validation AND Path C's gate (and Path C's downstream LLM-result validation too) — still checking the old, much narrower `_COUNTRY_TO_REGION` dict instead of the alias groups.

**Fix — three coordinated changes, not one:**

1. **Path A (primary — prompt improvement, chosen approach, generalized to all countries).** Add an explicit new rule to `classify_ask_route`'s system prompt (`intent_gateway.py:~1043`, alongside existing rule 5) instructing the model to recognize a country regardless of punctuation, spacing, letter case, or which real-world form was used (common name, official name, ISO alpha-2/alpha-3, or well-known colloquial short form), and to always output the country's plain common name once recognized. Include a small, deliberately multi-region example set — not an exhaustive 251-country list — to teach the *pattern*, explicitly stated to generalize to any country, not just the ones shown:
   - "US" / "U.S." / "U.S.A." / "USA" / "US.A" / "America" → United States
   - "UK" / "U.K." → United Kingdom
   - "UAE" / "U.A.E" → United Arab Emirates
   - "S. Korea" / "South Korea" → South Korea
   - "Ivory Coast" / "Côte d'Ivoire" → Ivory Coast

2. **Paths B and C — fix `is_recognized_country()` itself.** Change `is_recognized_country()` (`engine.py:6445-6466`) to check `_country_alias_group()` (`engine.py:657-668`) instead of the narrow `_COUNTRY_TO_REGION` dict, and have it return the group's canonical common name rather than a bare boolean where callers need the resolved value. This function is the single shared validation gate for **three** call sites: Path B's hint validation (`ask_api.py:7471`), Path C's regex GATE (`engine.py:763`), and Path C's downstream LLM-result validation (`ask_api.py:4644`, inside `_llm_confirm_and_extract_country`). For Path C specifically, this is not a mere backstop — it's what lets an **already-built LLM recognition step** actually run: today, most punctuation/abbreviation variants never reach `_llm_confirm_and_extract_country()` at all because the gate in front of it rejects them first using the same old dict. Fixing this one function unblocks Path C's existing LLM call for every variant, not just the ones that happen to survive the gate by luck (like "US.A" truncating to "US" today). `derive_region()` (`engine.py:6469+`), which currently does its own separate `_COUNTRY_TO_REGION.get()` lookup, needs the same canonicalization applied before its lookup so it keeps resolving a region correctly for any alias form.

   **Path B design decision (Drama round, resolved):** should the bare-anchor-reply path also call an LLM to recognize the country? Considered and rejected LLM-first: Path B fires on effectively every quote conversation (a hot path), and the codebase's own precedent for "direct answer to a just-asked question" (`apply_answer`'s exact-whole-reply alias matching, commit `0381164`) is deliberately deterministic-only, with no LLM call. Adding an LLM call unconditionally here would tax every normal reply with latency/cost to solve a problem the alias table already closes.

   **Chosen design — deterministic-first, LLM as a scoped last-resort escalation, mirroring Path A's own layering (just inverted):**
   1. Try `_country_alias_group()` first (fast, free, deterministic) — resolves the reported bug class ("US.A", "U.K", "S. Korea", etc.) with zero added latency on the common case.
   2. **Only if that returns no match**, escalate to a single, narrowly-scoped LLM call ("is this text a country name — if so, which one?") to catch genuine misspellings the alias table can't enumerate (e.g. "Untied States", "Grmany") — a different failure class than punctuation/abbreviation variants, which no static table will ever fully close.
   3. If the LLM escalation also returns nothing, fall back to the existing re-ask behavior — an honest "I didn't recognize that" is preferable to a silent wrong guess.

   This keeps the hot path cheap for the overwhelming common case (alias match succeeds), only pays LLM cost on genuine misspellings (rare), and never silently fabricates a country the customer didn't actually state.

3. **Path A (secondary backstop, as originally planned) — normalize whatever the LLM does extract.** Before assigning `route_meta.country`, pass the raw LLM-extracted string through `_country_alias_group()` to resolve it to canonical form. With fix #2 in place this becomes partially redundant (since `is_recognized_country` will itself canonicalize downstream), but keeping it at the extraction point means `route_meta.country` itself carries the clean value forward, not just the eventual validation check.

**Why this order:** #2 is the highest-leverage single change (fixes B and C simultaneously, and backstops A) — but #1 is still required because Path A's problem isn't validation, it's that the LLM never produces a candidate string at all for the model to canonicalize; a validator can't fix a value that was never extracted in the first place.

**Verification:** re-run the originally reported case, plus the regression matrix below, covering all three paths, multiple regions, and both the reported bug class (punctuation/abbreviation) and the genuine-misspelling class Path B's LLM escalation is meant to catch. Every row must be run against the LIVE API (not just unit-tested against the alias-group function in isolation), matching this session's established discipline for the rest of the 50-case suite.
